# Core 인터뷰 결정 기록

기준일: 2026-09-23. 개별 사용자 답변의 근거다. 전체 [BRIEF](BRIEF.md) 승인 기록은 별도로 관리한다.

- C-D01 / C-D04: 사용자가 `우선 구체화 되어야 하는 것은 'B. 1차 Core Workbench … Phase 2는 후속 …'`이라고 명시했다. 이전 Phase 2 우선 구체화 선택을 대체한다.
- C-D02: 이전 인터뷰의 `2-a` 답변을 유지한다.
- C-D03: 이전 답변에서 Codex CLI가 주력 후보지만 중요도가 낮고 Workbench를 잘 만드는 것이 우선이라고 했다.
- C-D05: 사용자는 프로젝트에 맞는 짧은 AGENTS.md를 요청했다. 상세 workflow는 기존 contract로 연결한다.
- C-D06: 역할·화면 인터뷰의 `1-a` 답변. Manager는 논의·계획·코드 수정, worker는 실험 실행·로그 분석·보고를 맡는다.
- C-D07: 같은 인터뷰의 `2-a` 답변. Manager·worker·terminal 세 영역을 한 화면에 표시한다. 후속 C-D20에서 기존 OMP TUI 재사용 방향을 선택했다.
- C-D08: 실행 정책 인터뷰에서 사용자는 `1-a와c가 좀 섞이면 좋겠는데 어느정도 manager가 알아서 처리`하기를 원했다. 승인과 자율 판단을 결합하는 방향을 채택하며, 구체 정책은 제안과 구분한다.
- C-D09: 최초 worktree 답변은 검토 의향이었다. 후속 C-D12에서 기본 운영 절차와 가이드 적용을 결정했다. 전용 자동 관리·차단 검사와 실행 중 병렬 개발 기능은 아직 승인된 범위가 아니다.
- C-D10: 사용자는 `3-A 사용자가 직접 입력하고 수정도 가능`하기를 원했다. 제어권 인수·worker 자동 입력 정지·반환 후 확인 방향을 채택한다. 실행 중 코드 수정의 경계는 C-D13에서 해결했다.
- C-D11: 후속 답변 `1-a, 그리고 사용자가 허용한 범위 내에서.` 실패 후 코드 수정·재실행까지 허용하되 사용자 허용 범위·예산과 실행 종료 확인을 따른다.
- C-D12: 후속 답변 `2-a, 그런데 가능하면 worker가 코드를 실행할 때는 worktree를 만들어서 실행하는 것을 기준`으로 하기를 원했다. 운영 가이드로 시작하고 commit 기반 실행용 worktree 준비를 기본으로 삼는다.
- C-D13: 후속 답변 `3-a`. 실행 중인 코드·설정을 직접 수정하려면 해당 실험을 먼저 중단한다.
- C-D14: Commit·관측·한도 인터뷰의 `1-a`. Manager가 위임 범위의 local commit을 만들 수 있는 제품 동작에 동의했다. 이는 현재 저장소를 commit하라는 요청이 아니다.
- C-D15: 같은 답변의 `2-a`와 `주기적(1분) 로그를 확인해서 hang이 의심되면 프로세스를 확인하는 작업`. 주기를 1분으로 명시하고 hang 조사를 추가한다.
- C-D16: 같은 답변의 `3-b 시간을 한도로 두지 ... 재시도 횟수 ... 가능하면 자동화 ... 수정 가능하고 개선 가능하다고 제시한 범위에서는 자동`. 작업별 시간 예산 제안을 채택하지 않고 세션 공통 설정·실행 시간 제한 없음·범위 내 자동화를 선택했다.
- C-D17: 모델 호출·hang 처리·재시도 인터뷰의 `1-a`. 매 1분 worker 모델이 새 로그와 상태를 판단한다.
- C-D18: 같은 답변의 `2-a`. Manager가 조사 근거를 검토하고 허용 범위에서 중단·수정·재실행을 결정한다. 불확실하면 조사·사용자 보고를 한다.
- C-D19: 같은 답변의 `3-a`. 세션 공통 설정을 각 작업에 적용하며 기본 자동 복구 재시도는 3회다. 최초 실행·정상 개선 실험과 구분하며 commit 변경만으로 횟수를 초기화하지 않는다.
- C-D20: 화면·종료 인터뷰의 `1-a`. 기존 OMP TUI와 명령을 최대한 유지한다. 구체 결합 방식과 호환 범위는 기술 검증으로 확정한다.
- C-D21: 같은 답변의 `2-a`. 화면만 분리하고 같은 host의 실험·agent·주기 점검은 계속한다. 명시적 전체 종료는 따로 두며 당시 남겨둔 전체 종료·OS 재부팅 정책은 C-D31/C-D32에서 해결했다.
- C-D22: 장애·수동 개입 인터뷰의 `1-a`. 재시작 후 기록·실제 프로세스 대조와 확인 가능한 작업의 자동 복구를 선택했다.
- C-D23: 같은 답변의 `2-a`. 모델 오류 중 실험·로그 수집 유지, 자동 판단·새 명령 일시 정지, 복구 후 상태 확인·재개를 선택했다.
- C-D24: 같은 답변의 `3-a`. 수동 제어 중 detach 시 사용자 제어권을 유지한다.
- C-D25: 같은 답변에서 사용자가 tmux 내부 사용을 거절했다. Workbench를 tmux 또는 herdr 안에서 사용할 예정이며 중첩 multiplexer 문제를 피해야 한다. 외부 프로그램 의존 대신 자체 화면·세션 관리로 구체화한다. 기존 tmux 기반 제안은 철회했다.
- C-D26: OS·호환 범위 인터뷰의 `1-a` 및 `윈도우는 안할꺼야. 맥도 안할 계획이지만 호환을 염두`. Linux만 초기 지원하고 macOS 향후 대응을 고려한다.
- C-D27: 같은 답변의 `2-a`. 텍스트 조작 우선, inline image 후속을 선택했다.
- C-D28: 같은 답변에서 `docs/OMP_Workbench_Development_Spec_v0.3.md` 참조와 `python을 메인으로 개발`을 요청했다. 참고 문서의 정책 표시를 기존 결정 변경이나 현재 구현 승인으로 취급하지 않는다.
- C-D29: 참고 스펙의 분석·peer wake 한도 인터뷰에서 `1-a`. 주기 분석은 고정 횟수 제한 없이 활성 실험 동안 계속하고 사용량 표시·사용자 중지를 제공한다.
- C-D30: 같은 답변의 `2-a`. 정상 manager↔worker 대화에 고정 횟수 제한을 두지 않는다. 위임 범위·재시도 한도·중복 처리 방지는 유지한다.
- C-D31: 종료·재부팅·보존 인터뷰의 `1-a`. 명시적 전체 종료에서 실행 중 작업을 보여주고 사용자 확인 후 중단·정리한다. 사용자 종료를 실패 복구 대상으로 자동 재실행하지 않는다.
- C-D32: 같은 답변의 `2-a`. OS 재부팅 후 기록은 복원하되 환경·실행 조건을 확인하고 사용자가 승인한 뒤 새 실험을 시작한다.
- C-D33: 같은 답변의 `3-a`. 작업·명세·결과 요약은 보존하고 수집 원문 로그는 run당 64 MiB·프로젝트당 512 MiB로 제한한다. 이후 저장 잘림을 표시하며 실행·화면·관측은 계속한다. 실행용 worktree를 자동 삭제하지 않는다. 실험 프로그램의 결과 파일에는 이 로그 한도를 적용하지 않는다.

- C-D34: 자동화 시작·중지·점검 경합 인터뷰의 `1-a`. 사용자가 위임 범위를 승인하며 진행을 지시하면 자동화를 시작한다. 별도의 AUTO ON 조작을 요구하지 않는다.
- C-D35: 같은 답변의 `2-a`. 당시에는 자동화 일시정지 중 기존 실험과 1분 모델 점검·읽기 전용 hang 조사·보고를 유지하고 새 변경·실행을 보류하기로 했다. **일시정지 동작은 후속 C-D49가 대체한다.**
- C-D36: 같은 답변의 `3-a`. Worker의 사용자 대화·작성 중 입력을 우선하고 밀린 주기 점검은 최신 한 건으로 유지한다. 응답 가능한 시점에 점검하고 마지막 점검 시각·지연을 표시한다. 종료 이벤트는 즉시 기록·표시하며 모델 결과 설명은 응답 가능 시 전달한다.

- C-D37: 완료 판단·명세 변경 인터뷰의 `1-a`. Worker가 결과와 검증 근거를 보고하면 manager가 승인된 완료 조건에 대조해 완료를 확정하고 보고한다. 매번 사용자 최종 확인을 요구하지 않으며 근거 부족·조건 모호 시 확인을 요청한다.
- C-D38: 같은 답변의 `2-a`. 실행 중 명세 변경은 기본적으로 다음 실행부터 새 revision으로 적용한다. 현재 실행은 시작 당시 명세를 유지하고 과거 명세·결과를 보존한다. 사용자가 현재 실행에 적용하도록 지시하면 중단·종료 확인 후 수정·재실행한다. 즉시 중단·권한 철회처럼 현재 실행을 명시적으로 제한하는 지시는 즉시 반영한다.

- C-D39: shell 지원·worktree 준비 실패 인터뷰의 `1-a`. 첫 버전은 Linux의 Bash 5.x부터 완성한다. zsh는 후속이며 추가 가능한 구조를 고려한다. 지원하지 않는 shell을 임의로 바꾸지 않고 제한을 표시한다. 기존 Bash/zsh 동시 출시 제안은 대체한다.
- C-D40: 같은 답변의 `2-a`. Worktree 준비 실패는 worker가 원인을 보고하고 manager와 조정해 허용 범위 내 local commit 준비·새 경로 선택 등으로 자동 해결한다. 해결할 수 없거나 추가 권한이 필요하면 사용자에게 묻는다. 사용자 변경을 임의 삭제·stash하거나 개발 중 디렉터리에서 대신 실행하지 않는다. 첫 버전은 일반 도구와 운영 가이드로 적용한다.

- C-D41: 사용자가 `zsh가 설치되어 있어도 bash를 실행해서 할 수 있는거잖아? 그러면 일단 bash만 하는게 좋겠어.`라고 명확히 했다. 기본/login shell이 zsh여도 Workbench의 host terminal은 전용 persistent Bash로 시작한다. 사용자 기본 shell 설정은 변경하지 않는다. 최초 Bash 시작과 실행 오류를 우회하기 위한 매 작업 새 shell 시작은 구분한다. C-D39의 미지원 shell 제한은 기존 기본 shell이 zsh라는 이유로 Workbench 시작을 막는 의미가 아니다.

- C-D42: 사용자가 `bash 혹은 못해도 sh는 지원해야해.`라고 보완했다. Bash 우선, Bash가 없으면 sh로도 Workbench를 사용할 수 있도록 최소 지원 대상으로 포함한다. C-D39/C-D41의 Bash 전용 출시 범위를 확장하며 zsh adapter는 계속 후속이다. 기본/login shell 설정을 바꾸지 않고 전용 persistent shell을 시작한다. sh의 실제 구현별 자동 실행·관측·입력 경합을 검증해야 하며 Bash 시험만으로 sh 지원 완료를 선언하지 않는다.

- C-D43: 남은 운영 정책 네 항목에 대해 사용자가 `추천대로 해줘.`라고 답했다. 1-A: 사용자가 선택한 기존 conda/venv를 재사용한다. Workbench 자체 환경과 분리하며 새 환경 생성·패키지 변경은 위임받은 범위에서만 수행한다. 작업별 환경 생성을 기본으로 강제하지 않는다.
- C-D44: 같은 답변으로 2-A 채택. 당시에는 이미 시작한 현재 도구 작업 완료를 기다린 뒤 다음 변경을 막기로 했다. **후속 C-D49가 이 완료 대기·도구 B 별도 차단 기준을 대체한다.**
- C-D45: 같은 답변으로 3-A 채택. 일반 중단에 반응하지 않으면 강제 종료가 위임 범위에 포함되고 대상 프로세스를 확인할 수 있는 경우에만 manager 판단으로 강제 종료한다. 조건을 충족하지 못하면 사용자에게 묻는다. 중단 응답 대기는 실험 실행 시간 상한과 구분한다.
- C-D46: 같은 답변으로 4-A 채택. 작업 이력의 영속 저장에 실패하면 기존 실험과 가능한 관측은 유지하고 저장 복구까지 새 자동 실행을 보류한다. 원문 로그만 저장에 실패한 경우 누락을 표시하며 실행은 계속한다.

- C-D47: G1 검증 중 사용자가 `2 MiB 한도·전체 거절 (권장)`을 선택했다. Child가 입력을 계속 읽지 않아 queue 공간이 부족하거나 paste가 2 MiB를 넘으면, paste를 일부 전달하지 않고 전체 거절하며 화면에 이유를 표시한다. 이 선택은 정상 크기 paste의 전달·원본 OMP 조작 검증을 면제하지 않는다.
- C-D48: G2 검증 중 사용자가 `명시적 handoff 허용 (권장)`을 선택했다. 사용자가 수동 입력 후 같은 shell에서 `wb-handoff`를 직접 실행해야 자동 실행 재개를 검토한다. 명령 자체가 안전한 clean boundary라는 증거는 아니며 Bash와 sh에서 실제 입력·job·cwd 상태 확인을 통과해야 채택한다.
- C-D49: 사용자가 Core Workbench 자동화 일시정지·worker 역할 정책을 새로 결정해 C-D35/C-D44의 충돌하는 부분보다 우선하도록 지시했다. 일시정지 요청 즉시 새 자동 지시를 보류하고 manager OMP의 진행 중 turn에 Esc와 같은 중단을 요청한다. 도구 A 완료 대기와 준비된 B의 별도 실행 전 차단은 보장하지 않는다. 요청과 실제 중단 확인을 구분하며 마지막 작업·확인된 파일 변경·실행 중 프로세스·미확인 결과를 표시한다. 일시정지 중 manager/worker의 새 자동 모델 작업과 1분 worker 모델 점검은 멈추되 로그·프로세스 수집과 기존 host 실험은 유지한다. 사용자 직접 조사·수정·rollback·명시적 agent 수동 지시는 가능하며 자동 재개를 뜻하지 않는다. Worker가 수정 필요성을 근거와 함께 manager에게 보고하면 그 지시에서의 역할은 끝나며 수정 후 자동으로 같은 작업을 다시 맡지 않는다. 재개 시 실제 파일·도구 결과·프로세스·작업 상태와 승인 범위를 대조하고 중단 명령·대기 요청을 replay하지 않는다. 취소는 기록·결과 파일의 자동 삭제가 아니다. UI 위치는 미결정이다.

(2) 보고 대기 표시와 불명 알림: worker 보고가 manager 입력창에 글이 있어 30초 넘게 대기하면 상태 줄에 이를 표시한다. 보고 전달 결과가 불명이면 manager에게 보고 내용 없이 "도착 확인 불가" 알림을 한 번 넣고, manager는 상태 조회로 내용을 받는다. (3) manager 전용 도구 `restart_worker`: 사유(필수)를 받아 Workbench가 띄운 worker OMP 프로세스만 종료(정상 종료 요청 뒤 유예 시간이 지나면 강제 종료)하고 기존 pane 재시작 경로(같은 OMP home, 역할 설정, 모델표, 격리 재확인)로 새 세션을 띄운다. 사용자 승인 없이 언제든 쓸 수 있고, 사유·시각·요청자는 재시작 기록과 화면에 남긴다. 이 경우 C-D62의 "실행 중인 OMP pane은 재시작하지 않는다"를 manager 요청에 한해 바꾼다. worker가 시작한 host terminal 명령은 그대로 둔다. 열린 Task는 취소하지 않는다. (4) OMP 재시작 복구(manager 판단): worker OMP가 새 세션이 되면(사용자 재시작, `restart_worker`, 비정상 종료 뒤 재시작) 열린 Task가 있을 때 manager에게 "worker 재시작" 알림을 넣고, 이어서 할지 취소할지는 manager가 정한다. 이어서 할 때는 같은 Task로 `to_worker`를 보내고, Workbench는 새 worker 세션에 Task 전체 명세(지시, 명령 목록, 지금까지 실행한 명령과 결과)를 다시 보낸다. manager OMP가 새 세션이 되면 Workbench가 새 manager 세션에 복구 알림을 자동으로 넣는다. 이전 세션에 보내지 못하고 버려진 worker 보고는 새 manager 세션으로 다시 보내고, 전달 결과가 불명이던 보고는 알림만 한다. (5) agent용 복구 skill과 상태 조회: manager에게 사용자가 직접 쓰지 않는 복구 skill을 두어 위 알림(점검 무반응·worker 재시작·도착 확인 불가·manager 복구)을 받았을 때 상태 조회 → 판단(후속 지시, 취소, `restart_worker`) 순서를 안내한다. manager 전용 읽기 도구로 열린 Task(지시, 명령 목록, 실행한 명령과 결과), worker 상태(쉼/응답 중, 세션, 재시작 기록), terminal 상태, 전달 대기·불명 보고와 그 내용을 돌려준다. backend 자체 재시작 복구는 CW-19 범위로 남는다.

- C-D71: 2026-10-08 CW-19(backend 재시작·재부팅 복구) 구현 전 사용자 결정. 근거: 설계 조사 result-p27-cw19-design-01.md. 사용자 인용: "전부 진행해서 테스트까지 해서 완료하고 보고해." 선택지 답변: 남은 프로세스 "manager가 판단해서 결정", 재시작 알림 "알림 1회 (Recommended)", 부팅 확인 전 "자동 동작 전부 (Recommended)", 세부 기본안 "둘 다 수용 (Recommended)". (1) 이전 backend가 띄운 프로세스가 backend 비정상 종료 뒤에도 살아 있으면(같은 boot에서 pid와 시작 시각으로 신원이 확인된 것만) Workbench는 자동으로 종료하지 않고, 그 목록을 manager에게 알리고 manager가 판단한다. manager는 상태 조회로 목록을 보고 전용 도구로 신원이 다시 확인된 개별 프로세스를 사유와 함께 종료하거나 그대로 둔다. 종료는 기록·화면에 남는다. 신원이 불명확한 프로세스는 종료 대상이 아니며 표시만 한다. 사용자는 상태 줄·status·전체 종료 목록에서 같은 목록을 본다. (2) 같은 boot에서 backend가 다시 시작되고 열린 Task가 있으면, 대조가 끝난 뒤 새 manager 세션에 "backend 재시작" 알림을 한 번 넣는다(남은 프로세스 목록 포함). 일시정지 중, 부팅 확인 전, 저장·모델 장애 보류 중에는 넣지 않는다. (3) boot marker가 바뀌어 재부팅으로 판정되면 사용자가 `confirm-boot`(CLI)로 확인하기 전까지 Workbench가 스스로 시작하는 동작(worker 지시 전달, worker `terminal`, 감시·복구 알림, 60초 점검, 새 실험)을 모두 보류한다. 사용자 직접 pane 입력, pane 재시작(C-D62/63), 인수, 일시정지·재개, 취소, 상태 조회는 허용한다. (4) 모델 오류로 생긴 해당 역할의 자동 작업 보류는 같은 역할의 다음 응답이 오류 없이 끝나면 자동으로 풀린다. Workbench는 확인용 모델 요청을 보내지 않는다. (5) 프로젝트 raw log 512 MiB 한도는 실험 run의 raw log에 적용하고, worker `terminal` 명령 로그는 명령당 64 MiB 한도만 둔다.

- C-D72: 2026-10-08 CW-16(최종 통합 검증) 착수 전 사용자 결정. 근거: 계획 result-p27-cw16-plan-01.md §9. 사용자 인용: "그냥 bash, sh만 지원으로 하자. 이거 둘중 하나는 무조건 있을거 아니야." 선택지 답변: OMP 버전 "18.8.0 기준 + 영향 대조 (Recommended)", worker 직접 요청 "범위 넘으면 manager 보고 (Recommended)", 승인 창 "해당 없음(근거 첨부) (Recommended)". (1) 지원 shell은 Bash(우선)와 sh(fallback)뿐이다. 사용자의 기본/login shell이 zsh 등 다른 shell이어도 Workbench는 Bash 또는 sh로 host terminal을 띄우며, zsh 전용 안내·실제 zsh login 검증은 C-AC-20 범위에서 뺀다. Bash와 sh가 모두 없을 때의 안내는 기존 구현대로 유지한다. (2) 최종 검증 OMP 버전은 설치된 18.8.0이다. OMP 18.2.10에 고정된 G1·G3 live probe 근거는 이전 기록(historical)으로 두고, 같은 사용자 동작을 18.8.0 최종 후보에서 다시 관측했는지 영향 대조표로 연결한다. 고정 probe는 실행한 OMP 버전을 기록하는 방식으로 바꾼다(CW-16 test delta). (3) 사용자가 worker에게 직접 요청할 때: 열린 Task 범위 안이면 그 Task로 수행하고, Task가 없는 작은 요청은 제한 없이 수행하며(C-D69 (6)(b)), 열린 Task 범위를 넘는 요청은 worker가 스스로 범위를 넓히지 않고 manager에게 보고한다(C-D69 (2)). (4) 원본 OMP 승인 창은 제품 구성(worker `--tools` 허용 목록, manager 기본)에서 나타나지 않으면 근거를 붙여 "해당 없음"으로 기록한다.
