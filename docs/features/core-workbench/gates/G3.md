# G3 — 공개 OMP extension·bridge feasibility

상태: **C-D49 기준 부분 검증, 전체 G3 통과 대기**  
관측일: 2026-09-24 (handoff 이후 probe 재개)  
대상: OMP `18.2.10` (`/home/dwchoo/.local/bin/omp`), Python `3.12.3`, Node `22.23.2`

## 현재 수락 기준 — C-D49

C-D49가 C-D35/C-D44의 충돌하는 일시정지 동작을 대체했다. 실제 manager OMP의 진행 중 turn에서 일시정지를 요청하고 공개 extension의 `ctx.abort()` 호출을 확인한다. 중단 **요청**과 OMP event로 확인한 **실제 중단**을 구분한다. 도구가 진행 중이었다면 마지막 작업, 확인된 파일 변경, 실행 중인 프로세스, 미확인 결과를 별도로 기록한다. 일시정지 중 bridge는 manager·worker에 새 자동 모델 작업을 전달하지 않는다. Gate harness가 실제 파일·도구 결과·terminal 프로세스·작업 상태·현재 승인 범위를 대조한 뒤에만 재개 신호를 보내고 중단 명령·대기 요청을 replay하지 않는지 확인한다. 실제 Workbench backend의 사용자 표시·대조와 1분 worker 모델 점검 보류, 로그·프로세스 수집 및 기존 host 실험 지속은 CW-11/12와 최종 통합에서 검증한다.

공개 `ctx.abort()`는 중단 요청 API이며 호출 반환만으로 실제 중단이나 도구 rollback을 증명하지 않는다. 도구 A 완료 대기·준비된 B의 별도 차단·read/report 모델 작업 지속은 현재 통과 조건이 아니다. 기존 해당 시험의 실패와 native approval 우회 가능성은 아래에 역사적 증거로 보존한다. 현재 제품 bridge는 manager의 진행 중 turn에 `ctx.abort()`를 요청하고, 실제 OMP event를 별도로 기록한다. 아래 실제 OMP 검증 범위 밖의 항목은 여전히 미확인이다.

## C-D49 후보의 실제 OMP 관측

`tests/gates/g3_omp/live_rpc_pause_probe.py --pair`를 실제 OMP `18.2.10`의 지속 RPC session 두 개와 제품 bridge로 실행했다. 독립 리뷰가 probe의 성공 판정 네 결함을 찾았고, test_designer가 수정한 최종 파일을 Root가 다시 실행해 exit `0`·`passed_pair_rpc`를 확인했다. Manager의 native `bash`가 임시 cwd에 `started.txt`를 만든 뒤 pause ACK `abort_requested`가 0.004초 만에 왔고, ACK 당시 `tool_execution_end`는 없었다. ACK에는 실행 중 tool ID가 미확인으로 표시됐다. 그 뒤 `agent_end`와 bridge의 `turn_stop_observed`를 관측했다. 이는 turn 종료의 관측이며, `ctx.abort()`가 도구를 rollback했다는 증거는 아니다. `result.txt`는 없었고 temp cwd의 잔여 process는 정리 후 0개였다.

종료 뒤 같은 session에 `probe`가 응답했고 `paused=true`, `abortStatus=stop_observed`, `unknownOutcomeToolCallIds=[pause-probe-bash]`가 남았다. `resume`은 대조 표시 없이 `reconciliation_required`를 반환했다. 최종 gate harness는 임시 cwd의 허용 파일 hash·추가 항목·symlink, OMP의 미확인 tool ID, 동일 process의 생존과 cwd process 집합, 테스트가 소유한 task/run·승인 범위를 다시 대조한 뒤에만 `reconciled:true`를 보냈고 `resumed`를 받았다. 승인·task·파일·symlink·process가 달라진 음성 사례는 모두 재개 신호를 보류했다. 이전 message ID의 재전송은 `unknown_no_replay`였고 미확인 tool ID는 재개 뒤에도 남았다. 테스트 전용 task/승인 fixture는 실제 Workbench backend의 기록·대조 구현을 증명하지 않는다.

별도 PID의 worker RPC session과 manager RPC session에서 `task`·`question`·`answer`·`report` 네 종류를 대상 session에 전달했다. 각 bridge ACK는 `api_accepted`, `modelProcessedAtAck=false`였고 전달 후 해당 OMP의 `agent_end` 증가와 scripted provider 요청을 관측했다. 최종 probe는 대상 OMP provider 입력에서 새 message ID·kind·task/revision/run ID와 answer/report의 reply ID가 정확히 일치하는지도 확인했다. 이전 메시지의 누적 context만으로 새 ID 검사가 통과하지 않는다. 성공 조건은 미확인 tool ID·turn 상태·재개 전 대조·두 OMP exit `0`·임시 cwd 잔여 process 0개를 포함한다. 정확한 provider 요청 index와 각 전달의 일대일 대응, 모델의 업무적 이해·답변 품질은 검증하지 않는다. Scripted provider·자동 승인·임시 경로를 사용했고 사용자 credential이나 요청·응답 본문은 보관하지 않았다. 재현 명령과 정확한 후보 hash·관측은 구현 run의 `cw04-cd49-pair-semantics-candidate.json`, `cw04-cd49-pair-semantics-result.json`에 기록했다.

별도 실제 OMP RPC 경합 probe에서 native `bash` 실행 중 `idle=false`, in-flight tool 1개, 도구 종료 event 이전에 자동 `report` 전달이 `deferred`였다. 200ms 관측 동안 provider 요청과 agent 시작 횟수는 각각 증가하지 않았다. Native `write`의 `--approval-mode=always-ask` 시나리오에서는 실제 approval pending event와 `approvalPending=true`, 파일 미생성 상태에서 전달이 `deferred`였고 200ms 뒤에도 승인 대기와 파일 부재가 유지됐다. 승인 응답을 보내지 않았다. 두 OMP 실행은 exit `0`, 임시 cwd 잔여 process 0개였다. Busy 시나리오만 tool 시작을 위해 `--auto-approve`를 사용했다. 근거는 `cw04-cd49-contention-final-candidate.json`과 `cw04-cd49-contention-final-result.json`이다.

ACK 유실·재연결 probe는 첫 `api_accepted` ACK가 host harness에 실제 도착한 뒤 한 번 폐기됐고 host ACK 목록에는 없음을 기록했다. Provider 입력의 task 식별자 일치와 `agent_end`를 관측한 다음 bridge socket만 닫았다. 새 hello는 같은 OMP PID·session ID·generation에서 왔다. 같은 message ID를 새 delivery attempt로 보내자 `duplicate_api_accepted`였고 provider 요청·`agent_end`는 각 1회로 유지됐다. OMP exit `0`, 임시 cwd 잔여 process 0개였다. 이는 즉시 재연결과 짧은 재시도 구간의 증거다. 근거는 `cw04-cd49-reconnect-final-candidate.json`과 `cw04-cd49-reconnect-final-result.json`이다.

## 2026-09-23 이전 기준의 재개 관측

수정된 no-tools 단일 task probe를 다시 실행했다. 두 독립 OMP process에서
`api_accepted`, provider request 1회, assistant exact marker와 `agent_end`를
약 3.4초 안에 확인했고 exit 0이었다. `after_provider_response` hook은 여전히
관측되지 않았다. 이는 worker 모델 응답 항목의 runtime 근거이며 전체 G3 왕복
근거는 아니다. 실행 기록은 구현 run의 `g3-single-task-resume-check.json`이다.

별도 실제 OMP v18.2.10 loop에서 같은 이름의 `write` wrapper가
`ctx.invokeTool`로 native write를 위임하는 것을 확인했다. Local scripted
provider가 한 assistant 응답에 A/B `write`를 함께 준비했을 때, wrapper가 B를
대기시키고 A 실행 중 pause를 수락한 뒤 A의 native write 완료, B의 native
시작 전 차단, `read`와 최종 보고의 지속을 확인했다. A 파일 내용은 정확했고
B 파일은 생성되지 않았다. 이 한 배치 probe는 `--auto-approve`를 사용했다.
Native approval은 앞선 별도 live probe에서 확인했으나 같은 배치와 approval의
결합, 제품 bridge에 wrapper 적용, peer 왕복·경합은 아직 검증하지 않았다.
`g3-same-batch-resume-check.json`과 `g3-preexec-wrapper-resume-check.json`에
명령·환경·관측을 분리해 남겼다. 당시 G3는 **pending**이었다.

후속 독립 테스트에서 제품 bridge의 mutable `write`/`edit`/`bash` 실행 직전
pause 경계가 미구현임을 재현했다. 한 차례 같은 이름의 `write` wrapper를
제품 코드에 적용해 auto-approved live write를 확인했으나, OMP 18.2.10의
`ctx.invokeTool`이 native tool의 입력별 approval을 다시 수행하지 않는다는
공개 API 근거가 나왔다. Native `bash`의 deny/prompt 규칙과 `write`의
path/device별 정책을 보존하면서 같은 wrapper로 실행 직전 pause를 검증할
방법은 현재 공개 API에서 확인되지 않았다. 승인 우회 가능성이 있는 wrapper는
제거하고 안전한 reply linkage 수정만 남겼다. 현재 G3는
**당시 public API approval 경계 때문에 blocked**였으며, 실제 정책 우회 실행을
검증했다는 뜻은 아니다. 근거는 구현 run의 `cw04-api-feasibility-audit.json`,
`cw04-resume-independent-tests.json`, `resume-unsafe-candidate-recovery.json`이다.

## 현재 재현 harness

저장소 루트에서 기본 명령은 실제 OMP 두 process의 extension load, local Unix socket handshake, idle/composer state만 확인한다. 기본 실행은 모델 prompt를 제출하지 않는다.

```bash
PYTHONDONTWRITEBYTECODE=1 python tests/gates/g3_omp/live_omp_probe.py
```

manager와 worker를 별도 OMP PID·PTY·working directory·session directory로 시작한다. CLI가 지정 extension만 로드하도록 `--no-extensions --extension <path>`를 사용한다. cwd, session directory, config overlay와 UDS는 모두 임시 디렉터리 아래 만들고 종료 때 제거한다. 기존 사용자 HOME 설정은 OMP가 읽을 수 있지만 이 probe는 이를 수정하지 않고 자격정보·응답 본문을 출력하지 않는다. `--no-tools`로 시작한다.

기본 handshake-only 실행: `PYTHONDONTWRITEBYTECODE=1 python tests/gates/g3_omp/live_omp_probe.py` — **exit 0**. manager/worker 두 독립 PID `3497312`, `3497313`; session generation은 각각 `1`; idle/empty composer 확인; provider request `0`회. 임시 process와 socket은 실행 종료 때 정리했다.

기존 후보에서 수행한 4개 message API enqueue(`task`/`answer`/`question`/`report`)의 `api_accepted` 결과는 `sendUserMessage(..., {deliverAs:"nextTurn"})` 사용 시 관측한 이전 candidate 기록이다. 이 invocation은 새 prompt를 시작하지 않았으므로 현재 extension의 model processing evidence로 보지 않는다.

Handoff 이후 live probe의 두 PTY를 실행 중 계속 drain하도록 수정했다. 출력 본문은 보관하지 않고 역할별 byte 수만 기록한다. 256 KiB를 쓰는 별도 PTY 배출 시험과 두 OMP handshake-only 실행은 통과했다. Handshake 실행에서 manager 12,570 byte, worker 10,663 byte를 배출했다.

bounded actual-model task 실행은 다음 opt-in 명령으로 수행한다. 기본 실행과 분리되어 있으며 worker에 task 하나만 보내고, OMP `--no-tools --max-time 45` 및 35초 전체 task deadline을 적용한다.

```bash
PYTHONDONTWRITEBYTECODE=1 python tests/gates/g3_omp/live_omp_probe.py --model-task-probe
```

이전 관측 결과: **exit 1**. Worker task ACK는 `api_accepted`, ACK의 `modelProcessed`는 `false`; 공개 `before_provider_request` hook으로 provider request 시작 `1`회를 확인했다. 35초 deadline까지 `after_provider_response` hook은 없었고, assistant marker와 `agent_end`도 관측하지 못했다. `--no-tools` 환경의 `tool_call` event는 `0`회였다. 당시 PTY를 drain하지 않아 timeout 원인은 미분류였다.

PTY 수정 후 같은 no-tools 단일 task를 **한 번** 재실행했다. 약 3.4초 만에 `api_accepted`, provider request 시작 1회, assistant의 일회성 exact marker 일치, `agent_end`를 관측했다. 도구 호출은 0회였고 manager PTY 111,308 byte, worker PTY 149,299 byte를 배출했다. `after_provider_response` hook event는 0회였으므로 당시 probe는 이 hook을 필수로 요구한 조건에 따라 **exit 1**을 냈다. 관측된 assistant marker와 `agent_end`는 worker의 모델 응답 완료를 뒷받침하며, 과거 35초 timeout은 PTY 미배출과 일치한다. 다만 timeout의 단일 원인을 확정하거나 provider response hook의 미발생 이유를 설명하지는 못한다. Probe의 통과 조건은 실제 assistant marker와 `agent_end`를 필수로 하고 response hook은 별도 진단값으로 분리했다. 이 변경된 조건으로 모델 요청을 추가 실행하지 않았다. 응답 본문과 credentials는 기록하지 않았다.

독립된 실제 provider auth probe는 no-tools/read-only `omp --print` 요청으로 수행했다. 최초 실행은 exit `0`, 정확한 `G3_AUTH_PROBE_OK` marker가 있었고 약 `2.6s`가 걸렸다. 위 task timeout 직후 고정 harness의 `--auth-probe`를 한 번 실행한 결과도 exit `0`, exact marker `yes`, 약 `2.3s`였다. 응답 본문과 자격정보는 기록하지 않았다. 이는 같은 CLI 환경에서 단독 모델 요청이 가능하다는 증거지만, extension이 시작한 TUI 요청의 응답이나 mailbox 처리를 입증하지 않는다.

## 정책 fixture

다음 명령은 protocol primitive의 fail-closed behavior만 확인한다.

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python -m unittest discover -s tests/gates/g3_omp -v
```

현재 C-D49 후보의 `node --experimental-strip-types --test tests/gates/g3_omp/bridge.test.ts`는 Root 재실행에서 **15/15 통과**, `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python -m unittest discover -s tests/gates/g3_omp -p test_g3_protocol.py -q`는 **7/7 통과**했다. Manager turn 중단 요청·관측, 미확인 결과 보존, paused 자동 전달 보류, 명시적 재개와 replay 금지, session 변경·전달 race를 fixture로 확인한다. 실제 OMP 검증은 위 RPC probe 범위에 한정된다. 이전 기준의 Node **7/11**, Python **6/6** 기록은 과거 mutable tool pre-execution wrapper 시험이며 C-D49 통과 근거로 사용하지 않는다.

## 아직 검증하지 않은 동작

- `after_provider_response` hook 미발생 원인, 정확한 provider 요청 index와 각 전달의 일대일 대응, 모델의 업무적 이해·답변 품질. RPC probe에서는 네 종류의 식별자·reply ID가 대상 provider 입력에서 일치하고 후속 `agent_end`가 증가함을 확인했다.
- 실제 OMP의 장기 재연결·지연된 중복 전송, session switch/generation 불일치. 즉시 ACK 유실·같은 session 재연결과 중복 message ID의 단기 재실행 금지는 관측했고 session 전환 경계는 Node fixture에만 있다.
- 실제 OMP의 non-empty composer 중 메시지 비침범과 장시간 busy·approval 경합. Busy native tool과 native approval pending의 전달 보류는 각각 200ms 구간에서 관측했다.
- 실제 Workbench backend가 마지막 작업·확인된 파일 변경·실행 중 process·불명 결과를 사용자에게 표시하고, 재개 전 파일·도구 결과·terminal process·작업 상태·현재 승인 범위를 대조하는 통합 경로. RPC harness의 `reconciled:true`는 이 제품 경로를 대신하지 않는다.
- 일시정지 중 manager·worker의 모든 새 자동 모델 작업과 1분 worker 모델 점검 보류, 사용자 수동 지시와 자동 재개의 분리, 기존 host 실험·로그·프로세스 수집 지속은 후속 production 통합 검증이 필요하다. 기존 `ToolPauseGate`와 A/B batch probe는 새 통과 조건을 대신하지 않는다.

따라서 CW-04 및 후속 gate를 위한 G3는 **부분 검증, 전체 통과 대기**다. 실제 OMP turn 중단 요청·종료 관측·미확인 결과 보존, 네 종류 전달의 provider 식별자·reply ID, busy·approval의 단기 전달 보류와 즉시 ACK 유실·재연결은 확인했다. Live composer·session 전환과 장기 경합은 미검증이며 backend 대조·사용자 표시·주기 점검 보류는 후속 production에서 검증해야 하므로 통과로 표시하지 않는다.

Probe는 공개 extension surface의 `session_start`, session manager, idle/pending 상태, UI composer text, `sendUserMessage(..., { attribution: "agent" })`, `before_provider_request`, `after_provider_response`, `message_end`, `tool_call`, execution/approval lifecycle hook만 사용한다. 공식 가이드는 `sendUserMessage`에서 `deliverAs`를 생략하면 idle session의 정상 prompt가 시작된다고 설명한다. Probe는 요청·응답 본문을 보관하지 않고 필요한 식별자 일치 여부와 digest만 기록한다. C-D49 기준 전체 G3 gate는 여전히 검증 대기다.
