# G2 — Bash/sh 같은 shell 실행 가능성

상태: **안전 결함으로 blocked / 부분 근거 확보**. Prototype은 Bash 5.2.21과
`/usr/bin/dash`에서 수동 `cd`/`export`를 거친 뒤 같은 프로세스에서 이어서
명령을 실행하고, foreground wrapper 명령 하나의 lifecycle을 control channel로
관측할 수 있음을 보였다. 승인된 G2 경계 전체를 입증한 것은 아니며, 후속 shell
구현을 승인하는 근거도 아니다.

## C-D53 종료 사실과 결과 판단의 경계

CW-03/G2는 `EVAL_RETURNED`, 관리 대상 local process의 실제 종료 확인과 확인 가능한
exit status, 종료 여부 `unknown`을 구분한다. 실패 exit도 종료가 확인됐다면 종료 사실이다.
Shell 반환만으로 남은 local 작업을 종료 처리하지 않는다. 로그·결과 파일 위치는 run에
연결하지만 내용으로 실험 성공·실패를 판정하는 일은 CW-10 worker 1차 판단과 CW-13
manager 2차 확인의 책임이다. `LOCAL_LIFETIME_DONE`은 관측한 local 수명 경계이며
그 자체로 실험 성공을 뜻하지 않는다. 비위임 host에서 안전한 종료 확인이 불가능하면
`LIFETIME_UNKNOWN`으로 보류한다. Writable delegated cgroup v2를 제품의 필수 환경
조건으로 확정하지 않았다.

현재 후보의 안전 결함은 별도로 남아 있다. 독립 실제 Bash·dash 시험에서 foreground
`dd`가 첫 6바이트를 소비한 뒤 같은 PTY write의 남은 줄을 `TAKEOVER_ACK`·`READY`
이후 shell 명령으로 실행했다. 또 초기 cgroup 이동과 rollback의 동시 실패를 주입한
독립 mock 시험에서 잔존 경로를 `close()`가 보고하지 못했다. 새 집중 테스트 8개 중
기존 6개는 통과했고 두 회귀 테스트가 Bash·dash 각각 실패했다. 따라서 G2는 계속
**blocked**다. 정상 `WAIT`에서 slave 입력 큐를 정리하는 후보와 control FD 손실·
Ctrl-C가 그 장벽을 우회하지 않는지 검증해야 하며, 정책 개정이나 exit 상태 구분만으로
안전 결함을 통과 처리하지 않는다.

후속 독립 경계 시험에서도 두 Bash·dash가 FD 8 EOF 뒤 `CONTROL_LOST`→`READY`로
돌아왔고, foreground `dd`가 소비하지 못한 줄이 `EOF_SPILL_EXECUTED` shell 명령으로
실행됐다. Control 대기 중 Ctrl-C에서는 대기하던 marker 실행은 관측되지 않았으나,
두 shell 모두 `needs_review=False`인 채 `READY`로 복귀했다. 집중 두 모듈의 10개
test 중 기존 spill/rollback 2개와 새 EOF/Ctrl-C 2개가 Bash·dash 각각 실패했다
(총 8 subtest failure). 이는 verified `WAIT`에서의 입력 flush만으로 모든 prompt
복귀 경로를 보호할 수 없음을 보여준다. Ctrl-C의 marker 실행을 재현했다고 쓰지 않는다.

## CW03-CONTROL-PROBE-001 — 전용 대기 판별 실험

2026-09-24 현재 checkout에서 기존 `prototype.py` 경로를 유지한 채 `control_probe.py`와
실제 shell 시험을 추가했다. Bash 5.2.21과 `/bin/sh`가 가리키는 dash에서 사용자
`cd`/`export` 후 직접 `wb-handoff`를 실행했다. 함수가 같은 interpreter에서 FD 8의
control 요청을 기다리고, `ACCEPT`→`START`→`DONE:0`을 FD 9로 보고했다. 요청은
PTY stdin에 쓰지 않았다. handoff 뒤 command 종료·다음 control 대기까지 `READY`
prompt event가 다시 나오지 않았고, shell PID·`/proc/<pid>/cwd`·export 값이 유지됐다.
이것은 이 host에서 핵심 실행권 가정이 성립한다는 **초기 관측**이며 G2 통과가 아니다.

| 짝지은 사례 | 관측 |
|---|---|
| 미제출 tail, 수동 background job | control 대기에 들어간 뒤에도 request 전송을 거절하고 `ACCEPT` 없음. job 사례는 shell job event로 `needs_review`를 유지했다. |
| Bash prompt hook이 `READY`를 먼저 보낸 뒤 지연 | 실제 `wb-handoff` 함수의 `WAIT` 전에는 request 전송 거절, `WAIT` 뒤 정상 수락. 이 재정의는 timing 대조용이며 지원 hook 조합의 증명은 아니다. |
| takeover 전송 전 | 요청 즉시 이후 전송 거절, `not_sent`와 별도 `TAKEOVER_ACK` 확인. |
| takeover `START` 뒤 | 이미 보낸 요청을 `unknown`으로 유지하고 새 전송 거절. foreground `head`의 별도 process group을 확인한 뒤 PTY로 수동 한 줄을 보내 완료·인수 ACK를 관측했다. 요청 replay 없음. |

재현: `PYTHONPATH=src python -m unittest tests.gates.g2_shell.test_control_probe -v`
→ 4 tests, exit 0. 원래 suite를 변경 전에
`python -m unittest discover -s tests/gates/g2_shell -v`로 재실행해 26 tests 중
22 pass, 4 fail(7 assertions), exit 1을 재현했다. 새 probe는 기존 실패를
통과로 바꾸지 않는다. 추가 후 같은 discover 명령은 30 tests 중 26 pass,
기존 4 fail(7 assertions), exit 1이었다. `git diff --check`는 exit 0이며,
종료 후 probe shell/job에 해당하는 실행 중 process는 관측되지 않았다.

### CW03-CONTROL-TRANSPORT-FIX-001 — 부분 record와 인수

독립 `test_control_boundaries.py`가 FD 8에 줄바꿈 없는 `RUN` 일부를 넣고
`request_takeover()`를 호출하자, 이전 수신기는 뒤따른 `TAKEOVER`를 명령 본문에
합쳐 실행했고 `TAKEOVER_ACK`도 내지 않았다. 수정 전 독립 테스트는 3개 중
1개 실패(Bash·dash 양쪽 subtest), exit 1이었다. 수신기는 이제 완성된
`RUN:...:__CW_END__` record만 수락한다. 인수 요청은 먼저 줄바꿈으로 미완성
record를 끝낸 뒤 별도 `TAKEOVER` record를 보낸다. 미완성 `RUN`은 거절되며
요청 즉시 새 자동 전송을 막는 latch와 이미 보낸 요청의 `unknown` 처리는 유지된다.

수정 후 실제 Bash/dash에서 독립 3개와 probe 4개가 모두 통과했다:
`python -m unittest tests.gates.g2_shell.test_control_boundaries tests.gates.g2_shell.test_control_probe -v`
→ 7 tests, exit 0. 전체 discover는 33개 중 기존 4개 실패(7 assertions)만
남아 exit 1이다. 독립 테스트는 수정하지 않았다. 이 framing은 단일 writer와
4096-byte 이하의 단일 pipe write를 사용하는 현재 probe 범위의 결과이며,
ACK 유실·임의의 외부 FD writer·전체 lifecycle 검증을 대신하지 않는다.

### CW03-CONTROL-LIFECYCLE-FIX-001 — 실행 중 인수와 job 반환

이전 probe는 foreground 자식이 PTY stdin을 기다리는 동안 shell이 `eval`에서
돌아오지 못하므로 인수 요청의 shell `TAKEOVER_ACK`가 지연됐다. 이제 host가
`START` event, PTY foreground process group, 현재 shell의 같은 session 후손을
대조해 `ForegroundTarget`을 별도로 확인한다. 이 확인은 shell ACK가 아니며,
확인된 process group이 유지되는 동안만 수동 입력을 보낸다. 실제 Bash/dash의
foreground `head`가 입력을 기다리는 0.1초 동안 ACK 없이 살아 있었고,
host 확인 뒤 PTY 수동 입력을 받아 종료한 다음 shell ACK를 보고했다.

`eval` 반환은 이제 `RETURN`으로 따로 관측한다. 그 직후 현재 shell의 job
목록과 후손 process가 남아 있으면 backend는 `ACTIVE_JOBS`로 분류하고
`DONE`을 만들지 않는다. 실제 `sleep 30 &`는 Bash/dash에서 살아 있는 job을
보고했고 인수 시 상태는 `unknown`, 인수 ACK 뒤에도 job은 살아 있었다.
Foreground가 종료하고 남은 job/후손이 없는 정상 명령에서만 `DONE`을 만든다.
현재 session에서 벗어나 재부모화된 daemon의 수명은 이 probe로 입증하지 못하며
전체 G2 lifecycle의 남은 검증 항목이다.

### CW03-CGROUP-LIFETIME-PROBE-001 — local cgroup 수명 경계

기존 `RETURN` 직후 shell job/후손 목록이 비었다는 이유로 `DONE`을 만드는
판정은 재부모화된 `setsid` daemon을 놓쳤다. 독립
`test_control_lifecycle.py`가 실제 Bash에서 daemon이 살아 있는데도
`DONE:escaped:0`이 나오는 반례를 재현했다. 현재 probe는 shell의
`EVAL_RETURNED`를 분리하고, delegated cgroup을 사용할 수 없는 실행에서는
`LIFETIME_UNKNOWN`을 유지하며 `DONE`을 만들지 않는다.

이 host의 사용자 delegated systemd scope 안에서는 shell을 먼저 수동 단계
cgroup에 넣는다. 직접 handoff 뒤 요청 전용 cgroup으로 **같은 PID**를 옮기고
이동을 `/proc/<pid>/cgroup`으로 확인한 다음 RUN을 보낸다. 수동 단계 cgroup에
기존 daemon이 남아 있으면 전송을 거절한다. RUN의 `RETURN`과 이어지는
`WAIT`를 본 후에만 shell을 수동 cgroup으로 되돌린다. 전용 cgroup의
`cgroup.events populated`가 1인 동안 local work를 보류하고, 0이 되면
`LOCAL_LIFETIME_DONE`을 낸다. 비동기 작업의 `LOCAL_LIFETIME_DONE`은
자동으로 `DONE`으로 바꾸지 않는다. control 손실/cleanup 경로는 전용
cgroup을 종료하고 잔존을 확인한다.

재현 명령: `systemd-run --user --scope -p Delegate=yes --unit=wb-cw03-e2e-20260924a /usr/bin/python -m unittest tests.gates.g2_shell.test_control_probe tests.gates.g2_shell.test_control_lifecycle tests.gates.g2_shell.test_control_boundaries -v`
→ 당시 14 tests, exit 0, 1 skipped(비위임 전용 시험). Bash/dash의 manual
`cd`/`export`와 PID를 유지했고, 수동 단계 daemon 차단, RUN 안의 재부모화된
daemon 생존 중 `populated=1`/`DONE` 없음, 자연 종료 뒤 `populated=0`,
foreground 인수와 부분 전송 회귀를 관측했다. control 손실 cleanup을 추가한
최종 집중 실행(`wb-cw03-verify-20260924a.scope`)은 15 tests, exit 0
(1 skipped)이었다. 추가 전 전체 discover는 40 tests 중 기존 prompt 경로
4 tests(7 assertions) 실패, 1 skipped, exit 1이었다. 최종 후보의 전체
discover는 재실행하지 않았다. 비위임 현재 checkout에서 probe 자체 8 tests는
exit 0(위임 전용 subtest 4개 skip)이지만, 독립 foreground 시험의 기존
`DONE` 기대는 비위임의 보수적 수명 정책과 충돌한다.

이 경계는 현재 host의 **local cgroup**에 남는 process만 다룬다. 외부 서비스,
remote job, 명시적 cgroup 탈출, scope가 사라진 뒤의 재접속 수명은 미검증이다.
systemd는 이 capability 실험의 fixture이며 제품 필수 의존성으로 결정하지 않았다.

### CW03-WAIT-BOUNDARY-CORRECTION-001 — 입력 유출 방지 재검증

독립 Bash·dash 테스트에서 발견된 foreground 입력 잔여분의 manual prompt 실행,
control FD 8 EOF 뒤 prompt 복귀, Ctrl-C 뒤 상태 미표시 복귀, 초기 cgroup 이동·rollback
동시 실패의 정리 경로 누락을 수정했다. 인수는 실제 `WAIT`에서 PTY writer lock을 잡고
현재 foreground 대상을 해제한 뒤 PTY **slave**의 `TCIFLUSH`가 성공해야 진행한다.
수동 foreground 입력의 부분 write와 오류는 bounded·fail closed로 처리한다. FD 8 EOF와
Ctrl-C는 `CONTROL_LOST`/`CONTROL_INTERRUPTED` 및 `CONTROL_STOPPED`를 내고
prompt로 돌아가지 않는다. cgroup 이동·rollback 실패의 잔존 경로는
`cleanup_residuals`에 보존한다.

최종 작은 OSError 수정까지 포함해 Root가 같은 후보에서
`PYTHONDONTWRITEBYTECODE=1 python -m unittest tests.gates.g2_shell.test_control_lifecycle tests.gates.g2_shell.test_control_boundaries tests.gates.g2_shell.test_control_probe -v`
를 실행한 결과 22 tests, exit 0, delegated 전용 6 subtests skip이었다. 같은 명령을
`systemd-run --user --scope -p Delegate=yes --unit=wb-cw03-root-final-20260924a`
안에서 실행한 결과 22 tests, exit 0, 비위임 전용 1 test skip이었다. 이 scope와
probe process는 종료됐다. 비위임에서는 `LIFETIME_UNKNOWN`을 유지한다.

**G2는 계속 미통과다.** FD 8 EOF·Ctrl-C 뒤 shell hold가 입력 유출은 막지만 현재
세션에서 수동 prompt로 복귀할 제어 경로가 없다. 같은 shell의 안전한 인수·복구
요구를 아직 입증하지 못했다. hook/trap 호환성, conda/venv, 다중 행·REPL·suspend,
ACK 유실·signal/exec, production adapter와 최종 독립 review도 남아 있다.
Delegated cgroup은 이 host의 capability 시험일 뿐 필수 환경으로 확정하지 않았다.

### CW03-CGROUP-REVIEW-FIX-001 — 완료·인수·정리 경계

Fresh review의 지연 drain 반례 때문에 `DONE`을 cgroup snapshot에서 만들던
판정을 제거했다. Shell `RETURN`은 `EVAL_RETURNED`, delegated local cgroup의
`populated=0`은 `LOCAL_LIFETIME_DONE`, 비위임은 `LIFETIME_UNKNOWN`으로
각각 남긴다. 짧은 재부모화 daemon이 첫 host drain 전에 끝난 Bash/dash 시험도
`DONE`을 내지 않았다. 이는 실험 전체의 성공·종료 판정이 아니다.

인수 요청은 즉시 latch하고 RUN 중에는 `TAKEOVER` record를 보류한다. Shell의
실제 `WAIT` event를 받은 뒤 delegated 경로에서 같은 PID가 run cgroup을
벗어난 것을 확인하고 record를 보낸다. 관리 대기 중 일반 PTY 입력은 거절하며,
확인된 foreground target의 수동 입력 또는 인수 ACK 뒤 새 `READY`로 확인한
manual prompt에만 보낸다. Bash/dash에서 RUN 중 queued manual 입력 차단,
foreground 입력 유지, shell 이동 뒤 ACK와 manual 명령을 관측했다.

`close()`는 bounded kill/reap/rmdir 후 남은 cgroup 경로를
`cleanup_residuals`에 보존하고 `CleanupIncomplete`을 발생시킨다. 실제
control 손실 cleanup과 주입한 residual 경로의 오류 보고를 시험했다.
비위임 `python -m unittest tests.gates.g2_shell.test_control_probe -v`는
12 tests, exit 0(위임 subtest 6 skip), delegated user scope의 같은 명령은
12 tests, exit 0(비위임 1 skip)이었다. 독립 두 파일의 delegated 6 tests는
기존 `DONE` 기대가 남은 2 tests(Bash·dash 4 subtests)에서 timeout, exit 1이다.
독립 테스트는 수정하지 않았고 현재 완료 의미와 기대의 불일치를 Root에 인계한다.

| 기존 실패 | C-D50 분류와 남은 의미 |
|---|---|
| Bash `builtin` override | 의도적 내부 helper/builtin 변조 경로. 보안 경계 밖이지만 해당 실행의 unsafe dispatch 관측은 보존한다. |
| dash `jobs` override | 의도적 내부 command 변조 경로. 일반 background job 차단의 면제가 아니다. |
| dash parent job after snapshot | `__wb_emit` 재정의로 snapshot 뒤 parent job 생성. 내부 변조 경로이며 snapshot 뒤 상태 변화가 기존 gate를 우회함을 보여준다. |
| Bash early READY before hook end | 재정의한 helper가 timing을 만들었지만 READY와 실제 입력 시점의 경합 자체를 재현한다. 새 probe는 `WAIT`가 실제 handoff 함수에서 발행되기 전 전송을 차단했다. 일반 hook 경합 검증은 계속 필요하다. |

남은 G2 항목: conda/venv와 비호환 hook/trap, 여러 줄·suspended job·REPL,
stale generation/owner, ACK 유실과 전송/수락 경계, control FD 손실·signal/exec,
지원 shell matrix·최초 자동화 승인 fixture. 이 probe는 단일 행 control 요청만
다루며 독립 test/review 및 production adapter 통합 전이다.

- 같은 사용자 권한의 고의적 내부 함수 변조/event 위조는 보안 경계 밖이다. 기존 실패를 개별
  분류하고 정상 입력/job 경합과 비호환 hook/trap 보류 사례를 유지한다. 분류만으로 pass 처리하지 않는다.
- 직접 `wb-handoff` 뒤 같은 interpreter가 prompt로 돌아가지 않고 전용 control 경로에서
  명령 하나를 기다린다. PID/cwd/export/검증한 conda·venv와 자식 stdin의 PTY 동작을 유지한다.
- 인수 요청 즉시 새 자동 전송을 막고 확인을 별도 기록한다. 이미 전송된 명령을 취소/종료로
  추정하지 않는다. 기존 실험을 유지하고 확인된 현재 foreground의 수동 입력을 제공한다.
  입력 대상 불명은 보류하며 오래된 요청을 replay하지 않는다.
- 실제 Bash/dash에서 정상 성공과 입력/job/인수 race를 함께 관측해야 production 범위를 넓힌다.
  최초 자동화는 승인+진행 조건을 따르며 수동 개입 뒤만 명시적 handoff를 요구한다.

[CW-03](../tickets/CW-03.md), [ADR-0002](../../../adr/0002-managed-shell-control-wait.md),
[진단](../DIAGNOSIS.md)에 판별 실험과 중단 기준이 있다. 구현 가능성은 아직 미검증이다.
아래의 초기 7개 시험·wrapper-only 설명은 **초기 탐색 시점**의 이력이다. 위의 네 번째 시도 후
22/26 기록이 현재 checkout에 관한 기존 최종 관측이며 초기 설명으로 대체하지 않는다.

## 초기 candidate에서 확인된 관측

| Bash 우선 선택, `sh` fallback, 선택한 실행 파일 고정 | Harness 통과 | `ShellSelectionTests` |

| foreground 종료 실패, REPL, shell 종료, nested shell | Candidate가 fail closed 또는 busy 유지 | `false`는 상태 1을 보고하고 다음 자동 전달을 막음. `read` 대기 중에는 완료 event가 없음. Shell 종료 시 DONE event가 없음. Nested interactive shell은 상태 미확인으로 대기 시간 초과 |

반복 가능한 harness는 제어 중인 PTY foreground process group과
`/proc/<pid>/exe`를 통해 foreground에서 동작 중인 nested Bash/dash도 확인했다.
Nested shell이 terminal을 소유하는 동안 gate는 `NEEDS_REVIEW`를 latch한다.
Harness 종료 과정에서 시작한 shell과 테스트 job의 process group을 모두 종료한다.

초기 탐색에서는 `jobs -p`를 command substitution 안에서 실행했다. Dash가 그
subshell에 현재 job table을 전달하지 않아 harness가 완료로 잘못 판단했다. 해당
결과는 폐기했다. 반복 가능한 prototype은 현재 shell에서 `jobs -p` 출력을 FD 9로
직접 보낸다. job이 하나라도 보고되면 이후 자동 전달을 차단한다.

## 초기 prototype의 입력 안전 경계

Input gate는 user와 automatic 입력을 하나의 lock으로 직렬화하고, shell generation과
owner epoch에 dispatch를 묶는다. 수동 입력은 control channel의 READY event 뒤에만
소비된 것으로 본다. 미완성 입력, 알 수 없는 편집 control, 아직 처리되지 않은 입력
행, 실패한 명령, 관측된 job, hook 유실 또는 lifecycle 미완료가 있으면 자동 전달을
비활성화한다. 이 관측이 유효하려면 PTY master를 backend가 독점해야 한다.

이 shadow-input 방식이 임의의 Bash Readline key binding, 여러 줄·이어쓰기 명령,
모든 paste 모드, shell의 `stty` 변경 또는 PTY 외부 writer와 함께 안전하게 동작하는지는
입증하지 못했다. 알 수 없는 byte는 보수적으로 처리하지만, 현재 시험이 가능한 모든
editor 상태를 다루지는 않는다. Dash의 prompt hook은 control-channel event를 내보내는
command substitution이다. 사용자 shell startup 설정을 온전히 보존하고 함께 구성할 수
있는지는 확인되지 않았다.

## 초기 탐색에서 남긴 미확인 항목

- Bash Readline 편집과 dash canonical 입력에서 REPL·여러 줄 paste를 포함한 임의의
  수동 입력 뒤 안전하게 clean 경계로 복귀하는 방법.
- 입력권 반환 전에 사용자가 시작한 background/suspended job. 현재 prototype의 직접
  `jobs -p` 확인은 automatic wrapper 완료 경로에만 연결되어 있다.
- 실행 중인 제품 backend에서 hook 유실 및 shell `stty` 변경 감지.
- 모든 shell 상태에서 취소된 명령과 hook 유실을 구분하는 Ctrl-C 동작. 결과가
  불확실하면 `NEEDS_REVIEW`로 남겨야 한다.
- daemon/detach된 후손 프로세스, hook을 교체하는 shell function, 직접 재현 범위 밖의
  noninteractive nested shell 및 `exec` 경계.
- 이 host의 Bash 5.2.21과 dash build 외의 shell 조합.

Bash와 선택된 `sh` 구현 모두에서 필수 입력·lifecycle 경계를 현재 근거로 확인하기
전에는 G2를 통과로 표시하지 않는다. clean 경계를 복구할 수 없는 경로는 수동 제어 또는
`NEEDS_REVIEW`에 남기며 새 shell로 조용히 재시도하지 않는다.
