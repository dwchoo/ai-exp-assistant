# G2 — Bash/sh 같은 shell 실행 가능성

상태: **안전 결함으로 blocked / 부분 근거 확보**. Prototype은 Bash 5.2.21과
`/usr/bin/dash`에서 수동 `cd`/`export`를 거친 뒤 같은 프로세스에서 이어서
명령을 실행하고, foreground wrapper 명령 하나의 lifecycle을 control channel로
관측할 수 있음을 보였다. 승인된 G2 경계 전체를 입증한 것은 아니며, 후속 shell
구현을 승인하는 근거도 아니다.

## 2026-09-23 재개 관측

승인된 C-D48에 맞춰 같은 shell에서 사용자가 직접 `wb-handoff`를 실행한 뒤에만
자동 입력을 검토하도록 후보를 고쳤다. 독립 테스트 21개는 Bash/dash에서
통과했지만, fresh review가 `PROMPT_COMMAND`/`PS1`의 문자열은 그대로 두고
호출되는 shell 함수를 재정의하는 경로를 발견했다. 이 경우 handoff의 job 검사
뒤 새 background job이 시작돼도 자동 입력이 허용될 수 있다. 따라서 C-D48
수정 단위의 review는 **실패**, G2는 계속 **pending**이다. 근거는 구현 run의
`cw03-handoff-review-2.json`과 `cw03-handoff-frozen-candidate-2.json`이다.

이후 사용자 승인 범위의 네 번째 bounded 수정에서 Bash·dash 실제 shell
회귀 사례 네 개를 검사했다. Bash `builtin` override, dash `jobs` override,
dash parent shell의 snapshot 이후 job, Bash hook의 READY 선발행 뒤 job
시작 경로가 자동 입력을 잘못 허용한다. 마지막 수정은 hook이 아직 완료되지
않았는데 `can_dispatch`가 참이 되는 독립 재현 사례 때문에 후보에서 제거했다.
현재 checkout의 `prototype.py`는 handoff 시점 코드이며, 독립 테스트
**26개 중 22개 통과·4개 실패(7 assertions)**다. 근거는 구현 run의
`cw03-fourth-independent-tests.json`, `cw03-fourth-blocked-candidate.json`,
`cw03-post-ready-independent-test.json`, `resume-unsafe-candidate-recovery.json`이다.
네 번째 수정 시도에 대한 최종 통과 review는 수행하지 않았다.

## 환경 및 재현 방법

- 환경: Linux, CPython 3.12.3, GNU Bash 5.2.21, `/usr/bin/dash`.
  이 host에서 `/usr/bin/sh`는 dash를 가리킨다.
- Harness는 `pty.fork()`로 실제 interactive shell을 시작한다. Backend가 PTY
  master의 유일한 writer다. Shell lifecycle event는 상속된 FD 9로 보내고,
  PTY 화면 출력은 별도로 읽으며 상태 판정에 사용하지 않는다.
- 저장소 root에서 실행:

  ```sh
  python -m unittest discover -s tests/gates/g2_shell -v
  ```

  이 candidate에서 확인한 결과: 테스트 7개 통과, process exit code 0 (1.3초).

## 확인된 관측

| 확인 항목 | 결과 | 근거 |
|---|---|---|
| Bash 우선 선택, `sh` fallback, 선택한 실행 파일 고정 | Harness 통과 | `ShellSelectionTests` |
| 수동 `cd /tmp`, `export CW03_G2_ENV=kept`, 입력권 반환 후 자동 명령 | Bash와 dash 모두 통과 | 같은 shell PID 유지. `/proc/<pid>/cwd`가 `/tmp`였고 FD 9에서 `STATE:/tmp:kept`, 이어서 명령 완료 상태 0을 확인 |
| 화면 출력·prompt와 분리한 lifecycle 관측 | 감싼 foreground 명령에서 통과 | FD 9가 `START`, `JOBS_BEGIN`, `JOBS_END`, `DONE:<id>:<status>`를 보고. READY도 FD 9의 shell hook event이며 PTY 출력에서 추출하지 않음 |
| background 및 suspend된 직접 자식 job 보고 | Bash와 dash 모두 통과 | Shell function이 현재 shell에서 `jobs -p >&9`를 실행. `sleep 30 &`와 Ctrl-Z로 suspend된 `sleep 30`에서 `JOBS_BEGIN`/`JOBS_END` 사이에 PID가 보고됨. 명령 상태가 0 또는 148이어도 PID가 있으면 `NEEDS_REVIEW`로 latch |
| 미제출 입력과 bracketed paste | Candidate가 fail closed | Backend 입력 shadow가 미완성 입력을 dirty로 유지하고 paste/control sequence에서 불확실 상태를 latch. 자동 입력은 보내지 않음 |
| foreground 종료 실패, REPL, shell 종료, nested shell | Candidate가 fail closed 또는 busy 유지 | `false`는 상태 1을 보고하고 다음 자동 전달을 막음. `read` 대기 중에는 완료 event가 없음. Shell 종료 시 DONE event가 없음. Nested interactive shell은 상태 미확인으로 대기 시간 초과 |

반복 가능한 harness는 제어 중인 PTY foreground process group과
`/proc/<pid>/exe`를 통해 foreground에서 동작 중인 nested Bash/dash도 확인했다.
Nested shell이 terminal을 소유하는 동안 gate는 `NEEDS_REVIEW`를 latch한다.
Harness 종료 과정에서 시작한 shell과 테스트 job의 process group을 모두 종료한다.

초기 탐색에서는 `jobs -p`를 command substitution 안에서 실행했다. Dash가 그
subshell에 현재 job table을 전달하지 않아 harness가 완료로 잘못 판단했다. 해당
결과는 폐기했다. 반복 가능한 prototype은 현재 shell에서 `jobs -p` 출력을 FD 9로
직접 보낸다. job이 하나라도 보고되면 이후 자동 전달을 차단한다.

## Prototype의 입력 안전 경계

Input gate는 user와 automatic 입력을 하나의 lock으로 직렬화하고, shell generation과
owner epoch에 dispatch를 묶는다. 수동 입력은 control channel의 READY event 뒤에만
소비된 것으로 본다. 미완성 입력, 알 수 없는 편집 control, 아직 처리되지 않은 입력
행, 실패한 명령, 관측된 job, hook 유실 또는 lifecycle 미완료가 있으면 자동 전달을
비활성화한다. 이 관측이 유효하려면 PTY master를 backend가 독점해야 한다.

이 shadow-input 방식이 임의의 Bash Readline key binding, 여러 줄·이어쓰기 명령,
모든 paste 모드, shell의 `stty` 변경 또는 PTY 외부 writer와 함께 안전하게 동작하는지는
입증하지 못했다. 알 수 없는 byte는 보수적으로 처리하지만, 현재 시험이 가능한 모든
editor 상태를 다루지는 않는다. Dash의 prompt hook은 control-channel event를 내보내는
command substitution이다. 사용자 shell startup 설정을 온전히 보존하고 함께 구성할 수
있는지는 확인되지 않았다.

## 미확인 항목

- Bash Readline 편집과 dash canonical 입력에서 REPL·여러 줄 paste를 포함한 임의의
  수동 입력 뒤 안전하게 clean 경계로 복귀하는 방법.
- 입력권 반환 전에 사용자가 시작한 background/suspended job. 현재 prototype의 직접
  `jobs -p` 확인은 automatic wrapper 완료 경로에만 연결되어 있다.
- 실행 중인 제품 backend에서 hook 유실 및 shell `stty` 변경 감지.
- 모든 shell 상태에서 취소된 명령과 hook 유실을 구분하는 Ctrl-C 동작. 결과가
  불확실하면 `NEEDS_REVIEW`로 남겨야 한다.
- daemon/detach된 후손 프로세스, hook을 교체하는 shell function, 직접 재현 범위 밖의
  noninteractive nested shell 및 `exec` 경계.
- 이 host의 Bash 5.2.21과 dash build 외의 shell 조합.

Bash와 선택된 `sh` 구현 모두에서 필수 입력·lifecycle 경계를 현재 근거로 확인하기
전에는 G2를 통과로 표시하지 않는다. clean 경계를 복구할 수 없는 경로는 수동 제어 또는
`NEEDS_REVIEW`에 남기며 새 shell로 조용히 재시도하지 않는다.
