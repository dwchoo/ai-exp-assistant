  item으로 함께 확인한다. OMP private parser 추적 자체를 별도 제품 요구로 추가하지 않는다.
- 현재 curses 256색 근사는 원본 색상 fidelity 완료 근거가 아니다. 실제 대조가 남아 있다.

## 2026-09-23 재개 관측 (초기 진단)

`tests/gates/g1_vt/live_runtime_probe.py`에서 OMP `18.2.10` TUI를 실제
`PtySession`·`TerminalScreen`에 연결하고, 임시 cwd/profile/session directory와
loopback scripted provider를 사용해 승인 UI·도구 출력·resize·query reply를
계측했다. 사용자 설정은 변경하지 않았고 provider 응답 본문과 credential은
기록하지 않았다. 사용한 명령은 다음과 같다.

```sh
PYTHONDONTWRITEBYTECODE=1 /tmp/cw02-g1-venv/bin/python tests/gates/g1_vt/live_runtime_probe.py
PYTHONDONTWRITEBYTECODE=1 /tmp/cw02-g1-venv/bin/python -m unittest discover -s tests/gates/g1_vt -p 'test_*.py' -q
```

첫 probe는 초기 prompt 인자를 사용했고 **exit 1**이었다. Provider 요청
0회, 승인 UI·도구 출력 미관측, PTY 출력 1,625,121 bytes 배출, VT parser의
query reply callback 8회를 기록했다. 두 번째 probe는 실제 composer 표시를
확인한 뒤 prompt와 Enter를 입력하는 방식으로 좁혀 재실행했다. Composer는
표시됐으나 provider 요청은 여전히 0회였고 **exit 1 / probe 미작동으로 인한
미확인**이다. 이때 PTY 출력 204,629 bytes를 배출하고 query reply callback
8회를 기록했다. 두 실행 모두 임시 경로와 OMP child를 정리했으며 해당 PID
`3660312`, `3661173`의 잔존 process를 확인하지 못했다.

Root가 제출 경로를 분리해 추가 진단했다. Prompt 입력을 보낸 뒤 화면 표시를
기다려도 입력이 보이지 않았고, 같은 PTY에서 `/clear` 확인 응답도 없었다.
Provider 요청은 계속 0회였다. 이 probe는 실제 TUI 입력이 수락됐음을
입증하지 못했으므로 승인·도구 출력 실패로 분류하지 않는다. 새 probe는
`input_visible_before_submit`와 `clear_ack`를 별도 진단값으로 보고한다.
마지막 실행에서는 composer 대신 화면에 `select`와 `provider` 문자열이
관측돼 입력 대상이 다른 UI일 가능성이 생겼다. 해당 UI의 상태와 원인은
확인되지 않았고, `--api-key`에 임시 값을 준 한 번의 재실행도 바뀌지 않았다.
임시 값은 최종 probe 코드에서 제거했다.

Query reply callback 호출과 PTY write 경로는 관측했지만, OMP가 그 답을
소비했는지와 실제 화면 복원은 증명하지 못했다. 두 번째 probe는 provider
request가 없어 승인·도구 출력·resize 단계를 진행하지 않았다. 첫 probe의
resize 검사도 승인 UI가 없는 상태의 화면 predicate에 의존했으므로 유효한
resize 실패 증거가 아니다. 이 결과를 OMP 자체의 기능 실패로 해석하지 않는다.
외부 tmux/herdr 실행은 이 bounded probe에서 수행하지 않았다. 기존 G1 fixture는
**21/21 통과**했으며, fixture 통과로 누락된 live 근거를 대체하지 않는다.

## 2026-09-24 실제 승인·도구 왕복

초기 입력 불능처럼 보인 원인은 격리된 OMP profile의 provider setup wizard였다.
임시 config에 `startup.setupWizard: false`를 지정해 wizard를 통과했다. 사용자
설정은 바꾸지 않았고 `--approval-mode=always-ask`를 유지했다. 실제 OMP
`18.2.10`의 composer에서 prompt를 전송한 뒤 native approval UI를 확인했다.
승인 UI가 보였을 때와 Enter 직전에 결과 파일이 없었고, Enter 뒤 실제
`bash` 도구가 파일을 만들고 그 내용을 화면에 출력했다. Scripted provider의
후속 요청과 최종 응답도 관측했다. Root의 마지막 재실행은
`approval_tool_scenario_passed=true`, `gate_status=pending`으로 종료했다.
이 성공은 승인·도구 왕복 시나리오에만 해당한다.

같은 probe에서 child와 screen을 100×32에서 84×24로 바꾼 뒤 approval
화면 요소를 관측했다. 그러나 resize 없이 `SIGSTOP→SIGCONT`만 수행한
대조 실행에서도 같은 redraw anchor가 나타났다. 따라서 그 화면 요소를
정상 resize 복원의 증거로 쓰지 않고 `normal_resize_confirmed=false`로
기록했다. Query reply는 9회·47 bytes를 PTY에 수락했고 noncanonical child
TTY 입력 큐가 비었음을 확인했다. OMP 내부에서 답을 해석했는지는
확인하지 못했다. 실제 terminal·외부 tmux/herdr 조합도 아직 미시험이다.

Root 재실행에서 G1 테스트 **29/29 통과**, 실제 승인·도구 시나리오 exit 0을
확인했다. 독립 delta review는 새 중대한 오탐을 찾지 못했으며 G1 전체
통과로 판정하지 않았다. 근거는
`.workflow/core-workbench/runs/implement-p2-20260923/cw02-resize-evidence-root-live.json`,
`cw02-no-resize-control.json`, `cw02-resize-evidence-delta-review.json`에 있다.
실행한 OMP child는 정리됐고 임시 probe 경로는 남지 않았다.

프로젝트 dependency는 추가하지 않았다. Python 3.12 가상환경에 prototype용 VT parser를 설치한다.


Live OMP probe는 두 실제 OMP 프로세스를 별도 controlling PTY에 띄운다. `--no-session --no-tools --no-pty --no-extensions --no-skills --no-rules --no-title`로 모델 요청과 도구 실행을 막고, composer 입력·한글·bracketed multiline paste·slash palette·`/clear`를 확인한다.

UI prototype은 xterm 형식 function key를 사용한다: F6은 다음 pane focus, F7/F8은 현재 pane scrollback, F10은 종료다. outer terminal에서 F6 두 번 뒤 host pane에 `printf 'G1_HOST_OUTPUT\n'`과 Enter를 보내 host output을 확인했다.

`omp --help`에서 `--approval-mode=<value>`와 `always-ask|write|yolo` 옵션은 확인했다. 초기 no-tools probe에서는 모델 요청과 도구 승인을 실행하지 않았다. 2026-09-23 재개 probe는 local provider 요청에 도달하지 못했지만, 2026-09-24 probe는 setup wizard를 지나 native approval과 실제 도구 실행에 도달했다.

## 2026-09-24 정상 resize 추가 관측 (CW-02 후보)

`omp/18.2.10`, `pyte==0.8.2`, Linux PTY, 격리된 임시 OMP profile과
`startup.setupWizard: false` 설정에서 다음 명령을 실행했다. OMP를 정지시키는
signal은 사용하지 않았다. 두 probe 모두 exit 0이며 finally에서 해당 child를
종료하고 임시 경로를 삭제했다.

```sh
PYTHONDONTWRITEBYTECODE=1 /tmp/cw02-g1-venv/bin/python tests/gates/g1_vt/live_normal_resize_probe.py
PYTHONDONTWRITEBYTECODE=1 /tmp/cw02-g1-venv/bin/python tests/gates/g1_vt/live_three_pane_resize_probe.py
```

첫 probe는 실제 OMP에서 한글 draft와 native approval 각각을
100×32→84×24→100×32로 변경했다. 두 단계 모두 VT screen과 child TTY의
geometry가 일치했고 draft/composer 또는 approval/command 표시가 유지됐다.
복귀 후 composer 입력을 추가하고 provider 요청으로 전송했다. 승인 직전까지
결과 파일이 없었고 Enter 승인 뒤 실제 tool 파일·화면 출력·후속 provider
응답을 확인했다. 동일 predicate를 적용한 no-resize 대조와 VT screen만 바꾸고
child PTY resize를 전달하지 않은 대조는 모두 실패했다. 세 시나리오의 OMP
child는 정리됐다. Resize 전 PTY 출력이 계속 나오는 일부 구간은 quiet 판정을
얻지 못했으며, 이 관측은 전체 출력 정숙을 전제하지 않는다.

독립 predicate 테스트 5개가 stale transcript marker, composer 안의 `approve`
문구, 준비 실패한 부정 대조, 초기 cross-routing, 잔존 child의 오탐을 확인해
probe 판정을 강화했다. 수정 뒤 G1 fixture 34/34와 두 live probe가 다시
exit 0이었다. OMP 18.2.10 composer는 `π >` label의 바로 다음 줄에 draft를
표시하므로 그 행 관계를 확인한다. VT buffer의 한 줄 길이는 이미 화면 폭으로
잘려 있으므로 이를 줄바꿈·잘림 없음의 근거로 쓰지 않는다.

후속 reviewer 지적에 따라 resize 뒤 새로 받은 PTY byte만 빈 동일 크기 VT
screen에 파싱해 draft/composer 또는 approval/command의 실제 재출력·행 위치를
판정했다. 기존 VT buffer와 child geometry만으로는 통과할 수 없게 했다.
Provider 요청 본문은 출력·보관하지 않고, 첫 user message에 원래 한글 draft와
`_INPUT_OK`가 이어진 문자열이 있는지만 boolean으로 확인했다. 3-pane은
매 단계 동일한 고유 child PID 3개와 관측한 모든 child의 종료를 요구한다.
최초 outer 240×45·child 78×41, 축소 outer 210×39·child 68×35,
복귀 outer 240×45·child 78×41도 각각 성공 조건에 넣었다.
이 강화 뒤 단일 OMP와 3-pane live probe가 각각 exit 0이었다. 여전히
줄바꿈·잘림·겹침의 시각적 완전 판정으로 확대하지 않는다.
추가한 post-resize byte·provider prompt·PID 안정성 단위 검사까지 포함한
당시 G1 focused test는 **37/37 통과**했다.
3-pane 첫 재실행은 12초 startup deadline 안에 두 OMP composer·host prompt가
모두 준비되지 않아 exit 1이었고, 관측된 세 child는 정리됐다. Bounded 재시도
1회에서 위 resize·routing·PID·cleanup predicate가 통과했다. 시작 지연의
빈도와 원인은 미확인이다.

추가 승인 predicate 검토에서는 단순한 `status: approve <result-file>` 출력도
이전 keyword 검사를 통과한다는 독립 반례가 발견됐다. 실제 OMP 18.2.10의
격리된 bash 승인 화면을 다시 관측해, `Allow tool: bash` 상단 테두리,
테두리 안의 결과 파일 command preview, 선택된 `Approve`와 다음 행의
`Deny`를 확인했다. 현재 probe는 이 구조가 현재 화면과 resize 뒤 새 PTY
byte 화면에 모두 있을 때만 해당 버전의 native bash 승인 화면으로 판정한다.
반례 테스트를 포함한 G1 focused test는 **38/38 통과**했고, 정상 resize의
전체 live probe도 exit 0이었다. 다른 OMP 버전·도구의 승인 UI로 일반화하지
않는다.

두 번째 probe는 실제 OMP 두 개와 host shell을 세 pane에 띄웠다. Outer PTY를
240×45→210×39→240×45로 바꾸자 각 child TTY가 78×41→68×35→78×41이
됐고 세 pane 제목과 manager/worker 한글 draft가 유지됐다. F6 focus 전환 뒤
worker draft에 추가 입력, host shell의 `printf` 출력, 복귀 후 manager draft에
추가 입력을 각 대상 pane에서만 관측했다. Outer app과 세 child가 종료됐다.

이는 이 PTY 조합의 `G1-RESIZE`·`G1-THREE-PANE`에 대한 후보 runtime 근거다.
새 화면 byte는 resize 뒤에 수신됐지만, 그 출력이 resize 때문에 생성됐는지까지
확정하는 근거는 아니다. 직전 출력과의 경합 가능성을 남겨 둔다.
실물 terminal/tmux/herdr, 색상 fidelity, 승인 상태를 포함한 outer 3-pane,
줄바꿈·겹침의 시각적 판정 및 다른 G1 item은 아직 미확인이다. 따라서 G1
전체 상태는 **미완료**다.

## 2026-09-24 외부 tmux 내부 실행 — 부분 근거

`timeout 90s env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src
/tmp/cw02-g1-venv/bin/python tests/gates/g1_vt/live_outer_tmux_probe.py`를
격리된 외부 tmux `3.4` socket 안에서 실행했다. 실제 OMP `18.2.10` 두 개와
host shell의 세 pane가 준비된 뒤 manager·worker·host 입력이 각 대상에만
표시됐다. Manager pane의 bracketed multiline paste, tmux window
240×44→210×38→240×44와 세 child TTY 78×40→68×34→78×40을 관측했다.
Root 최종 실행은 exit `0`, child PID `141090`·`141091`·`141092`와 tmux
server·app PID 모두 종료됐으며 격리 socket·directory도 제거됐다.

최종 probe는 실행별 sentinel을 primary VT에 놓고 tmux의 alternate screen
진입을 확인했다. 종료 뒤 client PTY에서 EOF까지 남은 130 byte를 파싱한
후 alternate screen 이탈과 sentinel 복원을 확인했다. 이전 후보는 client
종료를 감지한 직후 판정해 한 번 `local_vt_restored=false`였고, 남은 byte를
읽기 전 실제 복원 실패인지 구별할 수 없었다. 초기 두 실행에서는 pane 제목과
세 child PID는 보였으나 18초 안에 두 OMP composer가 보이지 않았다. 이후
진단본의 worker·Root 실행에서는 composer와 입력이 확인됐지만 초기 지연의
원인과 반복 빈도는 미확인이다.

현재 결과는 `G1-OUTER`의 외부 tmux 한 조합에 대한 부분 근거다.
일반 terminal·herdr, 색상 fidelity와 다른 G1 항목은
남아 있어 G1 전체 상태는 **미완료**다. 상세 결과는 구현 run의

독립 negative control은 이전 화면의 입력·paste marker가 남아 있기만 해도
