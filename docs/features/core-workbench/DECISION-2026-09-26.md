# C-D55: 환경 준비·수명 관측·개발 예산 결정

상태: 사용자 승인. 기준일: 2026-09-26. BRIEF r1.13 / SPEC s2.6 / PLAN p2.6에 반영한다.
기존 r1.12/s2.5/p2.5 및 Oracle 보완 승인과 Docker runtime 검증 생략을 유지한다.
이번 작업은 결정 문서화와 다음 세션 준비이며 제품 구현·runtime 검증은 수행하지 않는다.

## 사용자 결정 근거

현재 대화에서 사용자는 다음과 같이 지시했다.

> 1. 호출은 알아서 더 늘리면 되고.
> 2. conda는 점검하지마. conda 같은게 필요하면 터미널에서 직접 사용자가 환경 설정하고 agent는 내용만 넣어주면 될거 같은데? 우리가 만든 터미널은 사용자가 직접 조작할 수 있잖아. 그러면 사용자가 직접 설정하는거로 하면 좋겠어. 가능해?
> 3. 이건 어떻게 하면 좋겠어?

자동 실행의 관리 대상 후손을 추적하고, 수동 daemon의 소급 관리를 보장하지 않으며, 관측 불명 시 자동 후속 실행을 보류하고 cgroup을 필수화하지 않는 제안에 사용자가 답했다.

> 좋아 그렇게 결정하면 좋겠는데? 그러면 개발하는데 문제 없나?

이어서 결정 문서와 다음 세션의 implement 프롬프트 작성을 요청했다. 아래는 이 답변과 기존 승인을 결합한 현재 기준이다. 제품 검증 통과를 뜻하지 않는다.

## 환경 준비와 실행

- 사용자가 terminal 제어권을 인수하고, 안전하게 shell prompt로 복귀한 뒤 필요한 환경 활성화·cwd·환경 변수를 직접 설정한다. 실행 중 foreground 입력 인수와 shell prompt 복귀는 구분한다.
- Agent는 사용자가 준비한 환경에서 실행할 명령/script를 전달한다. 환경 관리자별 설치·activation/deactivation 자동화와 호환성 보장은 core의 완료 조건이 아니다. conda 전용 점검은 수행하지 않는다. 기존 venv probe 결과는 과거 근거로 보존하되 환경 관리자별 matrix를 확대하지 않는다.
- Workbench는 부모 shell의 PID·cwd·PATH를 포함한 exported environment를 유지하고 자동 실험 자식에 상속한다. Workbench 자체 Python 환경을 실험 환경에 주입하지 않는다. 비수출 변수·alias·shell 함수의 자동 복제는 보장하지 않는다.
- 수동 개입 뒤 사용자는 같은 shell에서 `wb-handoff`를 실행한다. 입력·job·identity·권한 확인을 거쳐 자동 제어 대기로 돌아간다. 최초 자동화에 별도 handoff를 강제하지 않으며 일시정지 중 handoff만으로 자동화를 재개하지 않는다.
- 실험 내부 cd·export·source 효과는 부모에 자동 반영하지 않는다. 일반 환경 상속·비전파, 정상 수동 준비와 비호환 hook/trap 보류는 계속 검증한다. conda 생략은 이를 면제하지 않는다.

## 수명 관측과 지원 경계

| 관측 | 동작 |
|---|---|
| 주 프로그램이 끝났지만 관리 대상 후손이 생존 | 전체 실험 수명은 실행 중으로 유지하고 다음 자동 실험을 보류 |
| 관리 대상 후손 전체의 종료·회수가 확인됨 | 종료 사실·확인 가능한 status를 기록하고 입력 반환 장벽 진행; 성공 판단은 worker/manager의 별도 책임 |
| Supervisor 사망·관측 channel 손실·관측 범위 밖 생성 등으로 수명 불명 | `unknown` 표시, 새 자동 실행·replay 보류; 완료나 종료로 승격하지 않음 |
| 수동 daemon 잔존 등으로 안전한 handoff를 확인할 수 없음 | 사유 표시 후 사용자가 정리하고 다시 전환; 정상 수동 환경 준비는 수락해야 함 |

고정 supervisor/subreaper 아래 자동 실행한 관리 대상 후손을 추적한다. Supervisor 이전에 사용자가 만든 모든 프로세스를 발견·소급 관리한다고 보장하지 않는다. 사용자 확인만으로 `unknown`을 종료 완료로 바꾸거나 귀속이 불명확한 프로세스를 자동 종료하지 않는다. 기존 승인된 중단·강제 종료의 권한/대상 확인 조건은 유지한다.

Delegated cgroup은 core 필수 조건으로 추가하지 않는다. 이번 결정으로 선택적 cgroup 구현을 추가하는 것도 아니다. 실제 한계 때문에 필수 권한·지원 shell·사용자 동작을 바꿔야 할 때만 실패 근거와 대안을 다시 제시한다.

## 개발 호출 예산과 재개

- 과거 누적 사용량은 220회다. 186회 opening + 해당 run 34회이며 journal revision 150, 예약 0, 활성 호출 0이다. 다음 세션에서 실제 ledger와 host 상태를 다시 대조한다.
- 기존 220회 사용자 상한은 이번 명시적 위임으로 후속 개발의 고정 상한이 아니게 된다. Root가 남은 구현·독립 테스트·review·수정·통합에 필요한 유한 operating budget을 산정하고 증액한다. 매 증액에 사용자 재승인을 요구하지 않는다. 사용량·실패 이력·host 제한은 보존한다.
- 과거 ledger와 승인 기록의 220회 상한은 당시 사실로 보존한다. 새 run에서 사용량을 0으로 시작하거나 operating limit만 추가해 기존 user limit을 우회하지 않는다.
- 현재 helper의 `limit` event는 기록된 user/host entry를 변경·제거할 수 없다. 새 세션은 이 문서와 새 승인 record를 근거로 원본 보존·명시적 supersession·누적 회계 대조를 갖춘 지원 가능한 전환 경로를 확인해야 한다. 단순 `ledger-update`나 `ledger-convert`가 이 정책 변경을 지원한다고 가정하지 않는다. 필요한 도구 보완은 구현 세션에서 별도 범위와 검증을 갖춰 처리하며, 이미 받은 예산 위임을 다시 묻는 문제로 바꾸지 않는다. 실제 dispatch 전 회계 전환과 유한 예산 예약을 완료한다.
- 이번 세션에서는 실제 journal 전환·증액·child 호출·제품 구현을 하지 않는다. 다음 세션에서 사용자가 아래 START 프롬프트의 `$implement`를 실행하면 기존 구현 승인과 이 결정을 이어받는다. Commit/push/게시/배포 승인은 없다.

## 남은 개발과 근거의 범위

CW-03 및 전체 core는 미완료다. 과거 predicates 8개 및 combined/lifecycle 25개 통과, env/launch live 10개 exit 0은 당시 후보의 제한된 근거다. Combined live 44개 기록은 TSTP unknown 6개·hard failure 0개로 exit 2 inconclusive다. 실제 suspend/resume, input-jobs, takeover/ACK-loss/no-replay, supervisor·FD·flush 장애, 수동 잔존과 관측 공백의 분류, 전체 G2 통합은 남아 있다. conda unavailable은 이번 결정 이후 완료 차단 사유가 아니며 지원 검증 통과로 바꾸지도 않는다. Docker는 skipped를 유지한다.

CW-02/04도 부분 검증 상태를 대조한다. CW-05는 CW-02/03/04의 필수 gate·통합 증거가 갖춰지기 전 진행 가능한 상태로 표시하지 않는다. 기존 CW-01 완료, 16개 ticket ID·의존 관계·소유·자원·write scope·필요 evidence level을 유지한다.

문서 개정은 runtime 증거가 아니다. 과거 수기 `final-root-check.json`을 정식 gate check로 간주하지 않고, 다음 구현에서 요구 identity·candidate·로그·item 결과가 연결된 근거를 남긴다. 변경된 문서 hash에 과거 pass를 재발급하지 않는다.
