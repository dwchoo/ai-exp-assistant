# CW-05: G4 detach 실증과 계약 고정

명세: [SPEC.md](../SPEC.md) s2.2. Scheduling·resource·scope의 원본: [PLAN.json](../PLAN.json) CW-05 항목. Live 상태와 작업 배정은 Root의 별도 workflow state에서 관리한다.

## 제공할 동작

G4: 분리된 frontend/backend 후보에서 backend가 세 PTY·두 OMP와 실제 periodic wake를 소유하고, detach 중 유지·재접속 시 중복 시작 방지를 실증한다. G1~G3의 성공 조합, OMP turn 중단 요청·확인/불명 결과 경계, 최소 metadata 저장 port를 통합 contract와 compatibility lock에 고정한다.

## 수락 기준

- G4: 위 제공 동작을 실제 조건에서 검증하고 재현 가능한 통과·실패·미확인 근거를 남긴다. 수락 ID는 직접 소유하지 않으며 후속 C-AC 검증의 선행 증거다.

## 계약과 선행 산출물

- CW-02: G1 PTY/VT 후보와 실제 OMP 화면 증거가 통합·검증됨.
- CW-03: G2 Bash/sh 실행·lifecycle 증거가 통합·검증됨.
- CW-04: G3 공개 extension·session 전달과 turn 중단 증거가 통합·검증됨.

선행 게이트의 검증된 조합만 사용한다. Backend crash 시 child 생존을 가정하지 않고 실제 process identity와 기록을 대조한다. 화면 연결 ID와 Task/run/OMP session identity를 구분한다. Metadata 저장 port는 write 성공·실패를 새 자동 실행 수락 경계에 전달하며 실제 schema는 CW-09가 소유한다.

계획 write scope: `src/workbench/runtime/**`, `src/workbench/contracts/**`, `src/workbench/app/**`, `tests/gates/g4_*/**`, `pyproject.toml`, `uv.lock`, `omp_bridge/package.json`, `docs/features/core-workbench/gates/G4.md`. 실제 dispatch 전에 Root가 current base·소유권·resource claim을 다시 확인한다.

## 검증

Frontend 종료 후 60초를 넘겨 두 OMP/host command/review wake가 살아 있는지 확인하고 재접속을 반복해 중복 PTY/run 여부를 본다. Backend/agent crash와 재부팅 모의 경계를 분리한다. 저장 port의 성공·실패 주입이 새 자동 실행 수락을 허용·보류하는 계약 시험을 추가한다. G3의 turn 중단·일시정지 결과와 정확한 toolchain 명령·dependency source/hash/라이선스·독립 테스트·review 결과를 기록한다.

공통 검증: worker quick check → 독립 test_designer 평가/필요 테스트 → 동결 후보 fresh reviewer → 필요한 수정·delta review → Root 통합 및 SPEC의 최종 check. 명령·cwd·candidate·환경·결과를 기록한다.

## 범위 밖과 중단 조건

G1~G3 미통과, 세 PTY 또는 review 지속 불가, 재접속 중복 실행이면 production ticket을 열지 않는다. 요구 행동 변경이 필요한 대안은 BRIEF 재합의로 돌린다.

Phase 2·내부 외부 multiplexer·무단 commit/push/merge·미승인 제품 동작 확대는 이 ticket의 범위가 아니다.

## 산출물 인계

변경 경로와 근거를 특정한 candidate/output bundle, 실제 수행한 check와 미실행 사유, 실패·미확인 gate/acceptance, 다음 ticket이 소비할 계약 변경점을 Root에게 전달한다. Ticket 작성자가 PLAN/state/approval을 직접 바꾸지 않는다.
