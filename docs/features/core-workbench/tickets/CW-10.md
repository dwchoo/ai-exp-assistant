# CW-10: 승인 Task에서 host run까지

명세: [SPEC.md](../SPEC.md) s2.4, 입력 [BRIEF r1.11](../BRIEF.md). 최초 구현 승인과 C-D53 정책 개정은 현재 run의 승인 기록을 따른다.
Scheduling·resource·write scope의 원본: [PLAN.json](../PLAN.json) `CW-10`. Live 상태/배정은 Root workflow record에서 관리한다.

## 제공할 동작

하나의 승인된 목표가 manager 준비/허용 local commit, worker의 실행용 worktree 준비, 같은 host shell 실행, 종료 사실 기록, worker의 로그·결과 파일 근거에 따른 1차 판단/보고로 이어지는 수직 흐름을 완성한다. Worker 직접 요청도 기존 명세 또는 범위 안의 작은 새 명세에 연결한다.

## 수락 기준

- C-AC-03: 실제 host shell 실행·출력과 worker 실행 의뢰, 관리 대상 종료/unknown 및 확인 가능한 exit status·로그/결과 위치 기록. `P-C-AC-03`와 최종 I-FLOW, I-SHELL로 확인.
- C-AC-05: manager 준비·worker 실험/terminal 실행·관측, 종료 확인 뒤 사전 기준에 따른 로그·결과의 출처·내용·미확인과 성공/실패/판단 보류 1차 판단 보고, 수정 필요 보고 시 지시 종료·새 지시 전 자동 반환 금지. `P-C-AC-05`와 최종 I-FLOW로 확인.
- C-AC-09: commit 기준 실행용 worktree 가이드·준비 실패 처리. `P-C-AC-09`와 최종 I-FLOW로 확인.
- C-AC-11: 위임 변경만 local commit·push/merge 분리. `P-C-AC-11`와 최종 I-FLOW로 확인.

## 계약과 선행 산출물

CW-07 shell, CW-08 mailbox, CW-09 TaskSpec/run을 소비한다. Worker 직접 요청이 승인 범위를 넓히면 manager 확인 전 실행하지 않는다. Worktree는 일반 Git 도구를 따르는 운영 가이드이며 자동 관리 기능이 아니다. 사용자 변경 삭제·stash·개발 디렉터리 우회, push·merge를 자동 수행하지 않는다. Worker가 코드 수정 필요성을 근거와 함께 manager에게 보고하면 그 지시는 끝나고, 수정 후 같은 작업은 manager의 새 지시가 있어야 한다.

선행 산출물·통합 경계는 PLAN의 이 ticket 및 `dependency_artifacts`를 따른다.

- CW-07: 실제 shell 수락·lifecycle·수동 제어가 통합·검증됨.
- CW-08: 연결된 manager/worker 메시지 전달이 통합·검증됨.
- CW-09: 승인된 불변 TaskSpec/run과 metadata gate가 통합·검증됨.

계획 write scope: `src/workbench/workflow/**`, `tests/workflow/**`, `docs/features/core-workbench/WORKTREE-GUIDE.md`. 실제 dispatch 전에 Root가 current base·mutation lease·resource claim을 재확인한다.

## 검증

실제 worktree를 기준 commit에서 준비해 cwd/commit/실험 환경을 기록하고 run 결과를 Task/revision과 연결한다. 종료가 확인되면 정상 exit+성공 로그, 오류 exit+실패 로그, exit 0이지만 실험 기준 실패, 로그 부족으로 판단 보류를 각각 worker가 사전 기준·파일 위치·내용 근거와 함께 보고하는지 확인한다. 종료 자체가 불명확하면 worker 판단을 강행하지 않고 unknown과 추가 점검 항목을 전달한다. 일시정지 중 종료 사실·로그 수집은 지속하되 새 자동 worker 분석은 시작하지 않는다. 준비 실패는 worker 원인 보고→manager 허용 범위 해결→불가 시 사용자 확인으로 간다. Worker 직접 요청은 기존 Task 범위 안, 기존 Task 없는 범위 안의 작은 새 명세, 범위 확대의 세 사례를 확인한다. 마지막 사례는 manager 확인 전 실행되지 않아야 한다. 독립 test_designer와 reviewer가 관련 없는 변경의 commit 포함·경로 혼동을 살핀다.

소유 check의 기준은 `PLAN.gate_items`다. 아래는 해당 항목의 요약이며 supplier/evidence의 원본은 PLAN이다.

| Item | 필요 근거 | 관측 |
|---|---|---|
| P-C-AC-03 | runtime | 실제 host shell 실행·출력과 worker 실행 의뢰, 종료/unknown 및 확인 가능한 exit status·로그/결과 위치 기록 |
| P-C-AC-05 | runtime | 종료 확인 뒤 worker의 출처·내용·미확인 기반 성공/실패/판단 보류 1차 판단 보고, 수정 필요 보고 시 지시 종료·새 지시 전 자동 반환 금지 |
| P-C-AC-09 | runtime | commit 기준 실행용 worktree 가이드·준비 실패 처리 |
| P-C-AC-11 | runtime | 위임 변경만 local commit·push/merge 분리 |

Worker quick check → 독립 `test_designer` 평가/필요 테스트 → 필수 실패가 해결된 후보 동결 → fresh `reviewer` → 필요한 delta 검증 → Root 통합. 기존 review는 유효 범위와 함께 재사용한다. 각 명령·cwd·candidate·요구 digest·환경·exit code·결과·unknown을 기록한다. Runtime probe는 PTY/pipe drain과 bounded cleanup/잔존 확인을 포함한다.

## 범위 밖과 중단 조건

기준 commit이나 필요한 dirty/untracked·외부 입력이 불명확하면 실행을 보류한다. 일반 도구로 안전한 준비가 안 되면 개발 디렉터리 실행으로 우회하지 않는다.

Phase 2·내부 외부 multiplexer·무단 commit/push/merge·미승인 동작 확대는 범위 밖이다. Gate item은 이 ticket 또는 전이적 선행 산출물만 사용한다. 후속 통합의 책임을 초기 통과 조건으로 요구하지 않는다.

## 산출물 인계

귀속 가능한 candidate/output bundle, 변경 경로, 수행한 check와 미실행 이유, 실패/unknown, 소비할 계약·지원 조합을 Root에 전달한다. PLAN/state/approval은 Root만 수정한다. Ticket 상태만으로 acceptance 완료를 표시하지 않는다.
