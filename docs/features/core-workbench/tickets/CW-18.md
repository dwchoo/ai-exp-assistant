# CW-18: Production 흐름·정책 조합

명세: [SPEC.md](../SPEC.md) s2.7 "Production 조합", 입력 [BRIEF r1.13](../BRIEF.md). [C-D56](../DECISIONS.md#C-D56)에서 승인한 후속 계획 변경이다.
Scheduling·resource·write scope의 원본: [PLAN.json](../PLAN.json) `CW-18`. Live 상태/배정은 Root workflow record에서 관리한다.

## 제공할 동작

CW-17 backend 안에서 이미 검증된 Task·workflow·점검·pause·복구 판단 부품을 하나의 실행 흐름으로 연결한다. 사용자는 제품 진입점과 CW-06 UI만으로 아래 흐름을 끝까지 진행할 수 있어야 한다.

1. Manager와 목표를 논의한다.
2. Manager가 TaskSpec 초안을 만든다.
3. 사용자가 위임 범위를 승인하고 진행을 지시한다.
4. Task/revision/run이 기록되고 worktree가 준비된다.
5. Worker가 persistent host run을 실행하고 60초 점검을 받는다.
6. Worker가 1차 판단을 보고하고, manager가 2차 확인한 뒤 완료·복구·보고한다.

- Manager의 Task 작성 경로: 현재 `bridge.ts`에는 manager가 TaskSpec을 만들 도구가 없다. Extension에 manager 전용 Task 초안·revision 작성 도구를 추가한다. 도구 호출은 초안만 만들고 승인이나 실행을 뜻하지 않는다.
- 사용자 승인: 위임 범위 승인과 진행 지시는 Workbench가 확인한 사용자 조작이어야 한다. Agent의 메시지나 도구 호출은 승인으로 보지 않는다(C-AC-29, 외부 접수와 실행 승인 분리). UI 위치와 키는 CW-06과 함께 구현에서 정한다.
- 흐름 연결: `TaskRepository.create_task/approve_scope/proceed` → `TaskWorkflow.start` → `G3WorkerResponsePort` → `WorkflowRun.collect/judge` → manager 보고 → `complete_run/fail_run` 순서로 잇는다. 첫 `LifecycleRecord`를 만들고 `bind_production`에 실제 입력을 제공한다.
- 주기 loop: backend 안에서 `LifecycleCoordinator.tick`, `WorkerReviewScheduler`, `PauseCoordinator`, `WorkflowObservationBinding`을 구동한다. 60초 점검·병합·일시정지 보류·turn 중단 요청/확인/불명·명시적 재개 대조를 UI 상태로 전달한다.
- 재시도·중단·명세 변경: 실제 종료를 확인한 뒤 승인 범위 안에서 수정·새 지시·재실행한다. 작업당 기본 3회 한도, 다음 실행에 적용되는 revision, 강제 종료 조건은 기존 CW-10~13 정책을 그대로 사용한다.

## 수락 기준

이 ticket은 아래 C-AC의 실제 진입점 결합을 local item으로 공급한다. 각 C-AC의 최종 판정은 CW-16의 I-FLOW·I-POLICY다.

- C-AC-01~05, 09, 11, 29: 실제 두 OMP와 scripted provider로 진입점에서 목표 논의부터 manager 완료 판단까지 한 흐름을 실행한다. 승인 전에는 자율 실행이 없어야 한다. Worker의 수정 필요 보고 뒤에는 자동 반환하지 않아야 한다. `L-CW18-FLOW`로 확인한다.
- C-AC-07, 10, 12, 13, 21, 25, 27, 30, 31, 33, 34: 같은 진입점에서 다음을 확인한다. `L-CW18-POLICY`로 확인한다.
  - 60초 점검과 병합
  - 일시정지 중 새 자동 모델 작업 보류
  - manager turn 중단 요청과 확인·불명의 구분
  - 명시적 재개 대조와 replay 금지
  - 재시도 한도
  - 실행 중 명세 변경이 다음 revision에 적용되는지
  - 강제 종료 경계

## 계약과 선행 산출물

선행 산출물·통합 경계는 PLAN의 이 ticket 및 `dependency_artifacts`를 따른다.

- CW-06: 세 영역 제품 UI와 상태 표시
- CW-10~13: Task→run, 점검, pause, 복구·완료 판단 정책
- CW-15: `LifecycleCoordinator`·`bind_production`·수명 불변식
- CW-17: backend process, data dir, `ui_v1`, OMP launcher

정책 부품의 동작은 바꾸지 않고 연결만 한다. 정책 결함이 발견되면 소유 ticket의 delta로 Root에 보고한다. Extension 도구는 CW-08의 전달 계약과 role 제한(`roleAllows`)을 유지하며 manager 전용으로만 추가한다.

계획 write scope: `src/workbench/app/**`, `src/workbench/backend/flow*.py`, `omp_bridge/g3/bridge.ts`, `tests/app/**`, `tests/bridge/test_manager_task_tool*`. 실제 dispatch 전에 Root가 current base·mutation lease·resource claim을 재확인한다.

## 검증

| Item | 필요 근거 | 관측 |
|---|---|---|
| L-CW18-FLOW | runtime | 실제 OMP 18.2.10 두 개(scripted provider)와 persistent shell을 쓴다. 진입점에서 승인 전 무실행, 승인·진행 뒤의 전체 흐름, worker 직접 요청의 세 경계, 수정 필요 보고 뒤 종료를 확인한다. |
| L-CW18-POLICY | runtime | 같은 진입점에서 60초를 넘는 점검·busy 병합, pause 중 보류와 수집 지속, 중단 요청/확인/불명, 재개 대조, 재시도 3회 한도, revision의 다음 실행 적용, 강제 종료 조건을 확인한다. |

Scripted provider는 runtime 근거이지만 실제 provider의 품질이나 인증을 검증하지는 않는다. 실제 provider 결합은 CW-16 I-FLOW에서 다시 확인한다. 독립 `test_designer`와 fresh `reviewer`를 거친다.

### 사용자 사용성 검토 (C-D57)

시작 전 UR-UX가 끝나 있어야 한다. 통합 뒤 UR-USABILITY에서 사용자가 실제 provider로 전체 흐름을 사용해 본다. 승인·일시정지 조작 위치나 문구 피드백은 이 ticket 또는 CW-06의 delta로 반영한다. UR-USABILITY가 끝나기 전에는 CW-16을 시작하지 않는다.

## 범위 밖과 중단 조건

다음은 이 ticket의 범위가 아니다.

- 다수 worker
- Phase 2 외부 접수
- 새 제품 정책
- 재부팅 복구: CW-19

Agent 메시지를 사용자 승인으로 취급하는 설계가 필요해지면 멈추고 보고한다. 기존 정책의 불변식(no replay, unknown 보류, 정확한 run identity)을 약화해야 한다면 구현하지 않는다.
