# CW-15: Detach·복구 대조·전체 종료

명세: [SPEC.md](../SPEC.md) s2.2. Scheduling·resource·scope의 원본: [PLAN.json](../PLAN.json) CW-15 항목. Live 상태와 작업 배정은 Root의 별도 workflow state에서 관리한다.

## 제공할 동작

정상 detach/재접속, agent/backend 재시작 대조, 재부팅 후 사용자 확인, 모델 오류 hold/recheck, 명시적 전체 종료를 사용자 상태와 실제 process에 연결한다.

## 수락 기준

- C-AC-15: detach 중 두 OMP·실험 유지, 자동화 활성 중 점검 지속·일시정지 중 보류와 재접속. 최종 I-FAULT에서 재확인.
- C-AC-16: 재시작 뒤 기록/실제 프로세스 대조·불명 자동 replay 금지. 최종 I-FAULT에서 재확인.
- C-AC-17: 모델 오류 중 실행·관측 유지와 재확인. 최종 I-FAULT에서 재확인.
- C-AC-18: 사용자 입력 owner를 detach 뒤에도 보존. 최종 I-FAULT에서 재확인.
- C-AC-22: 전체 종료 확인·중단/정리·미종료 표시. 최종 I-FAULT에서 재확인.
- C-AC-23: 재부팅 뒤 확인 전 새 실험 금지. 최종 I-FAULT에서 재확인.

## 계약과 선행 산출물

- CW-06: 세 영역 UI와 원본 OMP 직접 입력이 통합·검증됨.
- CW-08: OMP session ID와 불명 mailbox 처리 경계가 통합·검증됨.
- CW-11: 자동화 활성 중 detach 뒤 유지할 60초 점검과 일시정지 중 보류가 통합·검증됨.
- CW-12: 수명 전환 중 보존할 일시정지·취소 상태가 통합·검증됨.
- CW-13: 종료 확인과 manager 판단 경로가 통합·검증됨.
- CW-14: 영속 기록과 저장 장애 처리가 통합·검증됨.

CW-05의 분리된 lifetime contract와 CW-06/08/11/12/13/14의 통합 결과를 소비한다. 사용자 입력 owner·취소·일시정지를 복구가 해제하지 않는다. 일시정지 중 모델 점검을 시작하지 않고 재접속/복구도 자동 재개가 아니다. Backend crash 뒤 child 생존·PTY 재연결을 확인 없이 주장하지 않는다.

계획 write scope: `src/workbench/runtime/**`, `src/workbench/app/**`, `tests/lifecycle/**`. 실제 dispatch 전에 Root가 current base·소유권·resource claim을 다시 확인한다.

## 검증

Detach 후 세 process와 사용자 owner 유지, 자동화 활성 중 주기 점검 지속·일시정지 중 새 모델 점검 보류, 재접속 중복 run 없음, agent/backend crash의 살아 있는/사라진 process 대조를 확인한다. OMP auth/API 오류 중 마지막 모델 확인 시각과 실행·관측 지속, 복구 후 재확인, 재부팅 후 사용자 확인 전 새 run 금지, 전체 종료 전 사용자 확인과 미종료 표시를 검증한다. 독립 test_designer/reviewer가 replay·중복 시작을 검토한다.

공통 검증: worker quick check → 독립 test_designer 평가/필요 테스트 → 동결 후보 fresh reviewer → 필요한 수정·delta review → Root 통합 및 SPEC의 최종 check. 명령·cwd·candidate·환경·결과를 기록한다.

## 범위 밖과 중단 조건

실행·message 전달 여부를 알 수 없는 상태에서 자동 replay하거나 사용자 전체 종료/취소를 실패 복구로 되돌리면 중단한다.

Phase 2·내부 외부 multiplexer·무단 commit/push/merge·미승인 제품 동작 확대는 이 ticket의 범위가 아니다.

## 산출물 인계

변경 경로와 근거를 특정한 candidate/output bundle, 실제 수행한 check와 미실행 사유, 실패·미확인 gate/acceptance, 다음 ticket이 소비할 계약 변경점을 Root에게 전달한다. Ticket 작성자가 PLAN/state/approval을 직접 바꾸지 않는다.
