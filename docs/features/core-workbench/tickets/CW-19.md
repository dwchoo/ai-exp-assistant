# CW-19: Backend 재시작·재부팅 복구 조합

명세: [SPEC.md](../SPEC.md) s2.7 "Production 조합", 입력 [BRIEF r1.13](../BRIEF.md). [C-D56](../DECISIONS.md#C-D56)에서 승인한 후속 계획 변경과 격리 VM 재부팅 검증 환경을 따른다.
Scheduling·resource·write scope의 원본: [PLAN.json](../PLAN.json) `CW-19`. Live 상태/배정은 Root workflow record에서 관리한다.

## 제공할 동작

Backend가 시작될 때 UI 요청이나 자동 동작을 받기 전에 먼저 durable 기록과 실제 process·boot를 대조한다. 대조 결과에 따라 다음 네 경우를 구분해 처리한다.

- Detach 뒤 재접속
- Backend·agent 재시작 (종료된 OMP pane 단독 재시작은 [C-D62](../DECISIONS.md#C-D62)에 따라 CW-17·CW-06 delta가 제공한다. host terminal 강제 종료·재시작도 [C-D63](../DECISIONS.md#C-D63)에 따라 CW-17·CW-06 delta가 제공한다. 이 ticket은 backend 재시작 대조를 다룬다.)
- OS 재부팅
- 사용자 전체 종료

- Boot marker: `/proc/sys/kernel/random/boot_id`를 실제 boot marker로 사용한다. 기록된 marker와 다르면 재부팅으로 판정한다. 기록은 복원하고 환경·실행 조건 확인 화면을 보여준다. 사용자가 `confirm_boot`를 하기 전에는 새 실험과 자동 모델 작업을 시작하지 않는다(C-AC-23). 확인 표시와 `confirm_boot`는 CLI 진입점 명령으로 제공하면 충분하고 제품 UI 조작은 요구하지 않는다([C-D58](../DECISIONS.md#C-D58)). 제품 UI는 확인 대기 상태만 표시한다.
- 재시작 대조: 같은 boot에서 backend가 다시 시작되면 `LifecycleCoordinator.reconcile`과 `RecoveryCoordinator`가 기록과 실제 `/proc` identity를 대조한다. 확인 가능한 관측은 복구하고, 불명확한 것은 확인 대기로 두며 replay하지 않는다(C-AC-16).
- `RecoveryPort`: SQLite 기반 production 구현을 제공한다. `RecoveryCoordinator(object())` 같은 test 대체물을 production에서 없앤다.
- 종료 callback: `normal_stop`·`drain`·`force`와 termination 관측을 실제 workflow run에 연결한다. 전체 종료는 실행 중인 작업을 보여주고 확인을 받은 뒤 정리한다. 전체 종료는 CLI `shutdown`으로 충분하다(C-D58). 종료 확인에 실패하면 성공으로 표시하지 않는다(C-AC-22).
- 장애 표시: 모델 오류·metadata 저장 실패·raw log 한도/장애를 UI 상태에 연결한다. 이때 실행과 관측은 유지한다(C-AC-17/24/28).

### C-D71 결정 (p2.7t)

- 이전 backend가 남긴 프로세스(같은 boot, pid·시작 시각으로 신원 확인)는 자동 종료하지 않고 manager에게 알린다. manager가 상태 조회와 전용 도구로 개별 종료 여부를 정한다. 신원 불명은 표시만 한다([C-D71](../DECISIONS.md#C-D71)).
- 같은 boot 재시작 + 열린 Task이면 대조 뒤 manager에게 "backend 재시작" 알림 1회(일시정지·부팅 확인 전·장애 보류 중 제외).
- 재부팅 판정 뒤 `confirm-boot` 전에는 Workbench 자동 동작 전부 보류, 사용자 직접 조작은 허용.
- 모델 오류 보류는 같은 역할의 다음 정상 응답에서 자동 해제(확인 요청 없음). 프로젝트 512 MiB raw log 한도는 실험 run 로그만.

## 수락 기준

이 ticket은 아래 C-AC의 실제 진입점 결합을 local item으로 공급한다. 최종 판정은 CW-16 I-FAULT다.

- C-AC-16, 17, 22, 24, 28: backend process를 강제 종료한 뒤 진입점으로 재시작해 대조한다. 모델 오류, 저장 장애, 전체 종료 확인도 진입점에서 확인한다. `L-CW19-RESTART`로 확인한다.
- C-AC-23: 격리 VM 안에서 실제 OS를 재부팅한다. 재부팅 뒤 진입점이 기록을 복원하고, 확인 전에는 새 실험이 시작되지 않으며, 확인 뒤에만 시작되는 것을 확인한다. `L-CW19-REBOOT`로 확인한다.

## 계약과 선행 산출물

선행 산출물·통합 경계는 PLAN의 이 ticket 및 `dependency_artifacts`를 따른다.

- CW-13: `RecoveryCoordinator`와 복구·완료 정책
- CW-14: raw log 한도와 저장 장애 경계
- CW-15: `LifecycleJournal`·`LifecycleCoordinator.reconcile`·exact `RunIdentity`
- CW-18: 실제 흐름이 연결된 backend와 진입점

재부팅 검증 환경은 [C-D56](../DECISIONS.md#C-D56)의 격리 QEMU VM이다. 사용자 host는 재부팅하지 않는다. VM 안의 repo는 복사본이므로 검증 전에 현재 candidate와 같은지 대조하고, 입력 manifest에 VM 복사본의 hash를 기록한다.

계획 write scope: `src/workbench/app/recovery*.py`, `src/workbench/backend/boot*.py`, `src/workbench/policy/recovery_manager/port_sqlite.py`, `tests/recovery_boot/**`, `tests/vm/**`. 실제 dispatch 전에 Root가 current base·mutation lease·resource claim을 재확인한다.

## 검증

| Item | 필요 근거 | 관측 |
|---|---|---|
| L-CW19-RESTART | runtime | 실행 중 run이 있는 상태에서 backend를 SIGKILL로 종료하고 진입점으로 재시작한다. 기록과 실제 process 대조, 불명 run의 확인 대기와 no replay, 모델 오류 중 관측 유지, metadata 장애 시 새 자동 실행 보류, raw log 한도 뒤 실행 지속, 전체 종료 확인과 미종료 표시를 확인한다. |
| L-CW19-REBOOT | runtime | 격리 VM에서 진입점으로 run을 기록한 뒤 guest를 실제로 재부팅한다. boot_id가 바뀌었는지, 기록이 복원됐는지, 확인 전에 새 실험·자동 모델 작업이 없는지, `confirm_boot` 뒤에만 새 실험이 가능한지 확인한다. 재부팅 전후 boot_id와 명령·결과를 기록한다. |

독립 `test_designer`와 fresh `reviewer`를 거친다. VM 검증 명령에는 VM 이름, image checksum, guest 버전, repo 복사본의 manifest를 포함한다.

## 범위 밖과 중단 조건

다음은 범위가 아니다.

- 재부팅 뒤 backend 자동 시작(systemd 등록 등)
- 재부팅 전 실행 중이던 실험의 자동 재실행

사용자 host의 재부팅이 필요해지면 멈추고 보고한다. VM이 없거나 실행할 수 없으면 `L-CW19-REBOOT`를 pending으로 남기고, 통과로 기재하지 않는다.
