# Core Workbench 제품 동작 규약

Revision: r1.9; state: approved with external references. 작성일: 2026-09-23.
[BRIEF](BRIEF.md)의 C-D01~C-D49는 개별 합의이며, 합의 표시가 없는 P1~P4 세부사항은 합의된 행동을 구현하기 위한 설계안이다. r1.7 전체 문서 묶음 승인 근거는 [승인 기록](../../../.workflow/core-workbench/runs/approval-r1.7/approval.json)에 보관한다. C-D49는 C-D35/C-D44의 일시정지 동작보다 우선한다. 설계안의 실제 구현 가능성은 검증이 필요하다. 결정 근거는 [DECISIONS.md](DECISIONS.md), 용어는 [CONTEXT.md](../../../CONTEXT.md)를 따른다.
이 문서는 제품 동작이다. 저장소 개발 절차는 [workflow contract](../../../.codex/workflow-contract.md)가 정한다. 규약만으로 런타임 제어·격리가 구현되었다고 간주하지 않는다.

## 1. 역할, 위임과 작업 식별

**합의**

- Manager는 사용자와 논의·계획·코드 수정을 맡고 worker는 지시받은 실험과 terminal의 실행·관측·보고를 맡는다. Worker가 수정 필요성을 근거와 함께 manager에게 보고하면 그 지시에 대한 역할은 끝난다. 수정 뒤 같은 작업을 worker에게 자동으로 되돌리지 않으며 manager의 새 지시가 필요하다. 사용자는 두 역할과 직접 대화한다.
- 사용자가 허용한 수정·개선 범위 안에서 manager가 자동 진행한다. 같은 범위의 명령마다 승인을 반복하지 않는다. 범위 밖 행동은 추가 승인을 받는다.
- 세션 공통 설정을 각 작업에 적용한다. 실험 실행 시간 제한은 두지 않는다. 자동 복구 재시도는 작업당 기본 3회이며 최초 실행은 제외한다. Commit 변경만으로 초기화하지 않는다.
- 실패를 새 작업이나 정상 개선 실험으로 이름만 바꿔 한도를 우회하지 않는다. 정상 개선 실험은 승인된 목표·완료 조건 안에서 진행한다.
- 주기 점검·정상 peer 대화에 고정 호출 횟수 상한을 두지 않는다. 모델 사용량과 사용자 중지 수단을 제공한다. 실제 usage가 없으면 미확인/추정을 구분한다.

**P1 합의와 설계 상세화**

1. Manager가 목표, 변경 대상, 허용 실험·자원, 완료/중단 조건을 정리한다. [C-D34 합의] 사용자가 범위를 승인하며 진행을 지시하면 별도 AUTO ON 없이 자동화를 시작한다. 승인 전 자율 실행은 하지 않는다. 범위·명세를 표현하는 UI와 저장 형식은 계획 단계에서 상세화한다.
2. Task ID는 목표와 복구 이력을 연결한다. 실행마다 run ID를 붙이는 상세 식별 방식은 제안이다. [C-D38 합의] 실행 중 명세 변경은 새 revision으로 저장해 기본적으로 다음 실행부터 적용한다. 현재 실행의 명세·결과 이력은 덮어쓰지 않는다. 현재 실행에 적용하라는 지시가 있으면 중단·종료 확인 후 수정·재실행한다. 즉시 중단·권한 철회는 현재 실행에도 바로 반영하며 일반적인 다음 실행 변경으로 미루지 않는다. 세션 설정 변경은 이후 판단부터 적용하고 사용한 재시도 횟수는 유지한다. 이미 실행 중인 실험을 설정 변경만으로 종료하지 않는다.
3. Worker는 코드 변경 필요성을 근거와 함께 manager에게 보고하고 그 지시의 역할을 끝낸다. Manager는 실행 종료를 확인하고 허용된 코드를 수정·commit한다. 다시 worker 실행이 필요하면 새 지시를 보낸다.
4. [C-D37 합의] Worker가 결과·검증 근거를 보고하면 manager가 승인된 완료 조건과 대조해 완료를 확정하고 보고한다. 매번 사용자 확인을 요구하지 않는다. 근거가 부족하거나 완료 조건이 모호하면 확인을 요청한다. Exit code 0만으로 목표 달성을 확정하지 않는다. Exit code·결과 경로·관측 근거의 구체 기록 형식은 계획 단계에서 정한다.
5. 사용자 직접 worker 요청도 기존 명세나 작은 새 명세에 연결한다. 승인 범위를 넓히는 요청은 manager를 통해 확인한다.
6. [C-D49 합의, C-D35/C-D44의 충돌 부분 대체] 일시정지 요청 즉시 새 자동 지시를 보류하고 manager OMP의 진행 중 turn 중단을 요청한다. 도구 A 완료를 기다리거나 준비된 B를 별도로 차단한다고 약속하지 않는다. 중단 요청·실제 중단 확인·도구의 미확인 결과를 구분한다. 마지막 작업, 확인된 파일 변경, 실행 중인 프로세스와 미확인 상태를 표시한다. 일시정지 중에는 manager·worker의 새 자동 모델 작업과 1분 worker 모델 점검을 시작하지 않는다. 로그·프로세스 수집과 이미 실행 중인 host 실험은 유지하며 실험 종료는 별도 조작이다. 사용자 직접 조사·수정·rollback·명시적 agent 수동 지시는 가능하고 자동 재개를 뜻하지 않는다. 명시적 재개 때 실제 파일·도구 결과·terminal 프로세스·작업 상태와 현재 승인 범위를 대조한다. 중단 명령·대기 요청은 자동 replay하지 않으며 취소도 기록·결과 파일을 자동 삭제하지 않는다. UI 버튼·단축키 위치는 이 결정으로 확정하지 않는다.
7. 접수·실행 시작·업무 완료를 구분한다. 동일 메시지를 중복 처리하지 않고 session이 바뀌거나 전달 결과가 불명확하면 무조건 replay하지 않는다.

## 2. Commit과 worktree 운영 가이드

**합의**

- Worker는 기준 commit에서 별도 실행용 worktree를 만들어 사용하는 것을 기본 절차로 삼는다. 코드 수정은 별도 개발용 worktree에서 한다.
- 첫 버전은 일반 도구로 따르는 운영 가이드다. 전용 worktree 자동 관리·차단 검사 기능이나 실행 중 다음 실험의 병렬 개발 보장은 범위 밖이다.
- Manager는 위임된 변경만 local commit할 수 있다. 관련 없는 사용자 변경, push·merge 권한은 포함하지 않는다.
- 실행 중인 소스·설정을 수정하려면 먼저 해당 실험의 종료를 확인한다. 실행용 worktree를 자동 삭제하지 않는다.

**P2 합의와 준비 절차 설계안**

1. Manager가 기준 commit, 실행 명세, 필요한 설정·데이터·환경을 전달한다. Worker가 실행용 경로를 준비하고 실제 cwd·commit을 기록한다.
2. [C-D40 합의] Commit/worktree가 없거나 생성할 수 없으면 worker가 원인을 manager에게 보고하고 조정한다. 허용 범위의 local commit 준비·새 경로 선택 등은 자동 해결한다. 해결할 수 없거나 추가 권한이 필요하면 사용자에게 묻는다. 사용자 변경을 임의 삭제·stash하거나 mutable 개발 디렉터리에서 대신 실행하지 않는다. 기준 commit 변경 자체를 매번 재승인 사유로 삼지 않으며 기존 위임 범위를 따른다.
3. Branch 이름만 다르거나 같은 디렉터리에서 branch를 바꾸는 것은 파일 격리가 아니다. `stash`, `reset`, `clean`, 사용자 worktree 삭제를 암묵적으로 수행하지 않는다.
4. Commit은 외부 데이터·untracked 설정·환경 전체를 고정하지 않는다. 실행에 필요한 입력·출력 경로와 공유 GPU·환경 등의 충돌을 확인해 명세에 남긴다. [C-D43 합의] 사용자가 선택한 기존 conda/venv를 재사용하고 Workbench 자체 환경과 분리한다. 새 환경 생성·패키지 변경은 위임받은 범위에서만 수행한다. 작업별 환경 생성·복제를 기본 동작으로 강제하지 않는다.
5. 실행·개발 worktree 구분은 보안 sandbox가 아니다. 다른 editor 쓰기까지 막는다고 표시하지 않는다.

## 3. Host terminal과 사용자 제어권

**합의**

- 사용자가 terminal 제어권을 가져오면 worker 자동 입력을 멈춘다. 제어권 인수만으로 프로세스를 종료하지 않는다.
- 실행 중 소스·설정을 직접 수정하려면 먼저 중단하고 실제 종료를 확인한다. 사용자의 직접 명령 입력·로그 조회와 파일 수정은 구분한다.
- [C-D48 합의] 수동 입력 뒤 사용자가 같은 shell에서 `wb-handoff`를 직접 실행한다. 명령의 실행·현재 shell·미제출 입력·job·cwd를 확인하고 상태가 안전할 때만 자동 실행 재개를 검토한다. 반환 조작만으로 clean 상태를 추정하지 않는다. 사용자 제어권은 detach 후에도 유지한다.

**P2/P4 실행 경계 제안**

- Host terminal은 하나의 실제 persistent interactive shell이다. 그 shell에서 설정한 cwd·conda/venv·export를 유지한다. 부모 shell의 비수출 변수까지 자동 복제한다는 뜻은 아니다.
- Workbench 자체 Python 환경을 실험용 `python`·CUDA 환경으로 주입하지 않는다. Worker 명령을 별도 runner shell로 우회시키지 않는다.
- [C-D41/C-D42 합의] Linux에서 Bash를 우선 사용하고, Bash가 없으면 sh로도 동작하도록 지원한다. Bash 5.x가 우선 검증 대상이며 sh도 자동 실행·관측·사용자 입력의 핵심 흐름을 검증한다. 기본/login shell이 zsh여도 Workbench 전용 persistent Bash 또는 sh를 시작하며 사용자 기본 shell 설정은 바꾸지 않는다. 둘 다 사용할 수 없으면 시작 요건을 안내한다. 선택한 실행 파일과 실제 shell 구현을 표시·기록하고 검증한 지원 조합을 명시한다. zsh adapter는 현재 범위 밖이다. 시작 후에는 선택한 shell을 유지하며 실행 오류를 다른 shell로 우회하지 않는다.
- Shell 준비/시작/종료/exit code/cwd는 display output과 분리된 lifecycle 경로에서 확인한다. Prompt regex, 무출력, stdout의 가짜 marker로 완료를 판정하지 않는다.
- 하나의 foreground 실행을 다룬다. Busy, 미제출 입력, REPL, 입력 owner 불일치, cwd 불일치, 상태 불명 시 자동 입력을 보류하고 이유를 표시한다. 자동 명령 queue로 나중에 몰래 실행하지 않는다.
- Nested shell·background/daemon·`exec`·suspend·hook 유실은 자동 관측 경계를 표시한다. Prompt 복귀만으로 전체 작업 종료를 주장하지 않는다.
- 포커스와 입력 owner를 구분해 표시한다. 반환 시 실행·cwd·입력 상태를 재확인하고 명령을 자동 재전송하지 않는다.
- [C-D45 합의] 일반 중단에 반응하지 않을 때 강제 종료가 위임 범위에 포함되고 대상 프로세스를 확인할 수 있는 경우에만 manager 판단으로 강제 종료한다. 그렇지 않으면 사용자에게 묻는다. 사용자 입력 제어권과 일시정지 규칙은 계속 적용한다. 대상이 불명확하면 추정한 프로세스를 종료하지 않는다. 강제 종료 후에도 실제 종료를 확인하기 전 수정·재실행하지 않는다.
- 중단 요청·실제 종료를 구분한다. 종료 확인 실패는 중단 실패/확인 필요로 표시한다. 구체 signal 순서·중단 응답 대기 간격은 G2 검증으로 정한다. 이 대기 간격은 실험 실행 시간 상한이 아니다.

## 4. 1분 점검과 hang 조사

**합의**

- 자동화가 활성인 동안 활성 실험을 60초마다 worker 모델이 검토한다. 일시정지 중에는 새 모델 점검을 시작하지 않고 로그·프로세스 상태 수집을 계속한다. 새 로그가 없다는 사실도 판단 입력이다. 일반 코드가 출력·프로세스를 관측하고 모델이 해석한다.
- Hang이 의심되면 프로세스·자식 프로세스와 확인 가능한 자원 활동을 조사한다. 무출력만으로 hang을 확정하지 않는다.
- Manager가 조사 근거를 검토해 위임 범위·재시도 한도 안에서 중단·수정·재실행을 판단한다. 불확실하면 추가 조사 또는 보고한다.
- 사용자 제어권을 무시해 terminal에 조사·중단·재실행 입력을 보내지 않는다. 실험 실행 시간 상한을 hang 정책으로 대신 도입하지 않는다.

**P3 경합·지연 처리 — C-D36 합의 및 세부 제안**

- 자동화 활성 중 60초마다 점검 요청을 만든다. Worker가 바쁘면 pending은 최신 한 건으로 병합한다. 일시정지 시 새 요청과 pending 점검은 자동 시작하지 않는다. 주기와 실제 모델 점검 시각·지연을 구분해 표시한다. 정확히 60초 안에 분석 완료를 보장하지 않는다.
- 사용자의 직접 대화·미제출 입력·승인 대기를 우선한다. 자동 주입으로 진행 중 turn을 끊거나 입력을 제출하지 않는다. 입력/승인 경계가 풀리면 최신 상태를 검토한다.
- [C-D36/C-D49 합의] 종료 이벤트는 다음 tick까지 기다리지 않고 즉시 기록·표시한다. 자동화가 활성일 때 결과 설명은 worker가 응답 가능한 시점에 전달한다. 일시정지 중에는 결과 설명을 위한 새 자동 모델 작업을 시작하지 않는다. 오래된 점검을 완료 처리로 대체하는 세부 전달 방식은 제안이다.
- 사용자 terminal 제어 중에도 가능한 읽기 전용 프로세스 관측은 계속한다. 진단 기능이 없거나 권한 부족이면 미확인 이유를 보고하며 hang으로 단정하지 않는다.
- [세부 제안] 최신 로그·관측 요약은 원문 저장 상한과 별개로 제공한다. 이미 잘린 과거 원문을 복원할 수 있는 것처럼 보고하지 않는다.

## 5. 화면, detach와 종료·장애

**합의**

- 세 영역에 원본 OMP 두 개와 실제 host terminal을 함께 표시한다. Linux의 텍스트 조작을 우선하며 OS별 구현은 분리한다. 내부 외부 multiplexer 금지는 [ADR-0001](../../adr/0001-no-external-multiplexer.md)을 따른다.
- 화면을 닫으면 detach한다. 같은 host에서 실험·두 agent를 유지하고 자동화가 활성이라면 1분 점검을 계속한다. 일시정지 상태라면 모델 점검을 시작하지 않는다. 재접속은 기존 환경에 연결하며 사용자 입력 owner와 일시정지 상태를 보존한다.
- 명시적 전체 종료는 실행 중 작업을 보여주고 사용자 확인 후 중단·정리한다. 종료 확인 실패를 숨기지 않으며 사용자 종료 작업을 자동 재시작하지 않는다. 이 정리는 프로세스 종료이며 worktree·결과 삭제를 뜻하지 않는다.
- Agent/backend 재시작 시 기록과 실제 프로세스를 대조해 확인 가능한 관측을 복구한다. 상태 불명은 확인 대기이며 명령을 자동 replay하지 않는다.
- OS 재부팅 후 기록은 복원한다. 환경·실행 조건을 확인하고 새 실험은 사용자 확인 후 시작한다.
- 모델 API 오류·인증 만료 중 실험·일반 관측은 계속한다. 자동 판단·새 명령을 멈추고 상태와 마지막 확인 시각을 표시한다. 복구 후 현재 상태를 대조하고 기존 범위에서 재개한다.

**P4 표시·복구 제안**

- 화면 연결, 자동화 상태, 입력 owner, 실제 실행 상태, 마지막 모델 점검 시각을 구분해 표시한다. Backend crash 뒤 프로세스 생존을 확인 없이 가정하지 않는다.
- 복구는 확인된 상태를 다시 연결하는 동작이다. 사용자 취소·전체 종료·재부팅 뒤 새로운 실행을 일반 장애 복구로 우회하지 않는다.
- OMP 원래 단축키·붙여넣기·승인 조작과 wrapper 입력이 충돌하지 않도록 검증한다. [C-D47 합의] 2 MiB 한도를 넘거나 현재 queue 공간에 들어가지 않는 paste는 일부 전달 없이 전체 거절하고 화면에 이유를 표시한다. 정확한 키 배치·최소 화면 크기는 G1에서 정하며 세 영역 확인 요구를 임의로 축소하지 않는다.

## 6. 기록과 저장 장애

**합의**

- 작업·명세·결과 요약을 보존한다. 실행용 worktree를 자동 삭제하지 않는다.
- 수집 원문 로그는 run당 64 MiB·프로젝트당 512 MiB로 제한한다. 둘 중 먼저 도달한 한도부터 추가 저장을 멈추고 잘림을 표시한다. 기존 로그를 자동 삭제해 공간을 만드는 정책은 포함하지 않는다.
- 저장 상한은 실행·화면·일반 관측을 중단하는 신호가 아니다. 실험 프로그램이 직접 생성한 결과 파일의 크기는 이 한도 밖이다.

**P4 저장 실패 — C-D46 합의와 기록 설계안**

- [C-D46 합의] 작업·revision·실행·취소 등 metadata의 영속 기록 실패 시 저장 복구까지 새 자동 실행을 보류하고 장애를 표시한다. 실행 중 프로세스는 보존하고 가능한 관측은 계속한다. 기록 실패를 무시하고 메모리만으로 새 실험을 계속 시작하지 않는다.
- [C-D46 합의] Raw log만 쓰기에 실패하면 누락 이유·확인 가능한 구간을 표시하며 실험은 계속한다. 저장 복구와 실행 재시작을 혼동하지 않는다.
- 기록 위치·schema·회전 구현은 계획 단계에서 정한다. 수집하지 않은 로그나 손실된 상태는 복원 완료로 표시하지 않는다.

장애 복구는 사용자 일시정지·취소·권한 철회를 해제하는 동작이 아니다. 명시적 재개 판단은 실제 파일·도구 결과·terminal 프로세스·작업 상태, 사용자 제어권·승인 범위를 함께 확인한다. 중단 명령·대기 요청을 자동 replay하지 않는다.

## 7. 기술 후보와 후속 계획

Python 본체, 최소 TS 공개 OMP bridge, Textual·libvterm/CFFI, 분리된 display/control과 backend/frontend 수명이 후보 방향이다. 모델 호출·credential 관리는 기존 두 OMP에 두며 Python에 세 번째 판단 agent를 만들지 않는다. 구체 버전·배포·same-shell dispatch·독립 OMP 연결·detach는 BRIEF의 G1~G4 검증 대상이다.
[개발 명세 대조표](SOURCE-RECONCILIATION.md)를 함께 읽는다. 참고 문서의 자체 detach 제외, macOS 초기 지원, 재시도 0회, review 120회·peer wake 12회 제한을 현재 결정 대신 적용하지 않는다.
