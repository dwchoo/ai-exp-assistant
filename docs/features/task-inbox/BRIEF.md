# Task Inbox & Web Board — 요구사항 구체화 초안

Revision: r0.2; state: draft; 우선 구체화 보류.
작성일: 2026-09-23. 문서 전체 승인은 아직 받지 않았다.

## 문제, 사용자와 목표

- [PRD 기준] 외부 agent의 작업 요청을 보관하고 manager의 검토·토의를 거쳐 worker 실행 및 결과 조회까지 연결한다.
- [사용자 결정 D-01, 일부 대체됨] 1차 Workbench는 아직 없다. 최초에는 Phase 2 요구사항을 먼저 정리하기로 했으나, 우선 범위는 후속 D-04로 변경되었다.
- [사용자 결정 D-02] 최초 환경은 Workbench·외부 agent·사용자 브라우저가 같은 컴퓨터에 있는 localhost 구성이다.
- [사용자 결정 D-03] 첫 사용 client 후보는 Codex CLI지만 client 선택의 우선순위는 낮다. 사용자는 Workbench 자체의 완성도를 우선한다.
- [사용자 결정 D-04] 사용자가 1차 Core Workbench를 먼저 구체화하고 Phase 2는 후속으로 두기로 명시했다. 현재 인터뷰는 [Core BRIEF](../core-workbench/BRIEF.md)에서 이어간다.

## 공통 용어

[CONTEXT.md](../../../CONTEXT.md)를 따른다. Workbench의 제품 정의와 이번 인터뷰의 작업 범위는 구분한다.

## 범위와 비목표

- [PRD 기준] 요청 접수·조회·댓글, 검토 기록, 승인 명세 연결, 내부 전달, 실행 추적, 웹 조회, 결과 회수 및 영속 저장.
- [PRD 기준] Phase 2 구현은 1차 core 완성과 실제 실험 검증 이후에 진행한다. 요구사항 구체화는 먼저 진행할 수 있다.
- [PRD 기준] 범용 scheduler, 다중 worker, 원격 terminal 조작, 전체 대화 동기화, 파일 첨부 및 callback은 제외한다.
- [현재 작업] Phase 2 문서는 후속 요구사항 입력으로 보존한다. 현재 인터뷰 대상은 1차 core이며 Phase 2 구현·ticket 생성은 진행하지 않는다.

## 제약과 호환성

- [사용자 결정 D-02] 초기 접속 범위는 같은 컴퓨터의 localhost다.
- [사용자 결정 D-03] Codex CLI를 첫 사용 후보로 기록한다. 지원 버전·인증·호환성 검증 수준은 미결정이며, 호환성 확인이 끝났다는 의미가 아니다.
- [PRD 기준] Board 없이도 core가 동작해야 하며 Board가 host terminal이나 PTY를 소유하지 않는다.
- [PRD 기준] 요청 저장과 mailbox 통지를 분리하고, 저장 후 통지 실패로 접수 성공을 뒤집지 않는다.
- [PRD 제안, 미확정] 단일 서비스·단일 요청 저장소·단일 내부 adapter, SQLite 및 Streamable HTTP. 구체 기술 선택은 아직 승인되지 않았다.

## 공개 동작과 수락 예시

다음 항목은 [원본 PRD §14](../../OMP_Workbench_Phase2_Task_Inbox_PRD_v0.1.md)의 요구사항 입력이다. 이번 인터뷰에서 상세 설계까지 합의하거나 검증한 것으로 표시하지 않는다. 기존 P2-AC ID를 보존한다.

- P2-AC-01, 04: Board 없이 core를 사용하고, manager가 offline이어도 Board가 살아 있으면 접수·조회한다.
- P2-AC-02, 03: 접수는 완료를 기다리지 않고 ID를 반환한다. 같은 요청자·키·내용은 중복 생성하지 않으며 내용이 다르면 충돌로 처리한다.
- P2-AC-05, 06: 웹과 MCP에서 같은 기록을 조회한다. 질문·답변·재검토가 이어지며 조회는 모델을 호출하지 않는다.
- P2-AC-07, 08: 외부 요청은 실행 승인이 아니다. 승인 명세 연결, 전달 ACK와 실제 시작을 구분한다.
- P2-AC-09, 10: Command 성공만으로 요청을 성공 종료하지 않고, 새 요청이 실행 중 작업을 자동 선점하지 않는다.
- P2-AC-11, 12: 알림 병합에도 요청을 보존한다. 불명확한 실행은 자동 재전송하지 않으며 재시작·연결 상실·동기화 지연을 구분한다.
- P2-AC-13, 14: 요청자 권한과 안전한 웹 표시를 검증하고, 결과 조회로 비밀 정보나 임의 host 파일이 노출되지 않도록 한다.

## 결정과 근거

- D-01: 사용자 답변 `1-b`. 선행 core 부재를 확인했다. 최초의 Phase 2 우선 구체화 결정은 D-04로 대체되었다.
- D-02: 사용자 답변 `2-a`. 같은 컴퓨터에서 시작하므로 원격 직접 공개는 초기 설계의 전제가 아니다.
- D-03: 사용자 답변 `3-codex cli이지만 크게 중요하지 안을거 같아. 일단 workbench만 잘 만들면 좋겠어.` Client별 기능보다 제품 흐름을 우선한다.
- D-04: 후속 사용자 답변에서 `B. 1차 Core Workbench`를 명시적으로 선택했다. Manager 대화, worker 위임, terminal 실행·로그·결과 확인을 먼저 설계하고 Phase 2는 후속으로 둔다.
- 위 결정은 개별 인터뷰 답변이며 문서 전체 승인이나 구현 권한이 아니다. 현재 별도 ADR은 없다.

## 구현 방향과 검증 의도

- [PRD 기준] 요청 저장소, manager의 판단, worker의 실행을 구분한다. 명세·task ID·revision·실행 보고는 1차의 계약을 재사용한다.
- [미결정] 1차 계약이 없으므로 구체 API signature, 이벤트 payload, 파일 소유 범위, ticket 의존성과 작업 일정은 확정하지 않는다.
- [검증 의도] 접수 중복, 권한 경계, 알림 실패, 재시작, 실행 시작·종료 판정, 모델 호출 없는 조회를 관측 가능한 예시로 구체화한다.
- [검증 한계] 현재 구현이나 실행 테스트 결과는 없다. 원본에 인용된 외부 MCP/OMP 자료도 이번 인터뷰에서 재검증하지 않았다.

## 미결정·보류 사항

- Q-01: D-04로 해결. 1차 core가 우선이다.
- Q-02: Manager 검토 시작 방식, 사용자 위임과 승인 범위, 실행할 작업의 선택 경로.
- Q-03: 댓글 이후 재검토, 명세 revision 변경, 취소, 실패·재시도 및 재연결 확인의 사용자 흐름.
- Q-04: 로컬 인증과 역할별 조회·쓰기 권한, 공개 결과 범위.
- Q-05: 1차에서 정할 mailbox·명세·실행 상태·자동화 예산 계약을 후속 Phase 2 설계에서 확인한다. 현재는 해당 계약이나 통합 구현을 확정할 수 없다.
- Q-06: 저장 위치·보존 정책·입력 제한·client 호환성 검증 범위와 기술 선택.

## 인계

Phase 2 구체화는 보류하고 [Core BRIEF](../core-workbench/BRIEF.md) 인터뷰를 진행한다. 전체 BRIEF 승인은 없다.
Phase 2 재개 시 core의 실제 계약을 확인하고 남은 결정을 해결한 뒤 승인받는다.
향후 Phase 2 승인 후에만 새 Sol XHigh/Max 세션에서 `$to-tickets docs/features/task-inbox/BRIEF.md`를 사용한다.
