## 2. Gap analysis per ticket bullet

### 2.1 Boot marker (C-AC-23)
- **Missing**: durable recorded/confirmed marker for the data dir. `backend.json.boot_id` is the only one and is overwritten at `service.py:279` before being read. `LifecycleRecord.boot_marker` exists only once a run was bound and is the bind-time boot.
- **Missing**: classification at start (fresh / clean stop same boot / crash same boot / reboot / boot unknown); `require_boot_confirmation()` never called (`service.py:1293`); `confirm_boot` is in-memory (`service.py:688`) — a backend crash after confirmation would forget it, and a pre-confirmation crash would also forget the requirement (because the next start overwrites the record). Needs persistence before lifting.
- **Missing**: the hold itself. Nothing consults `boot` before automatic work. The hold points that exist for pause are: `flow.py:1042` (`_is_paused` → `held("paused")` on to_worker), `flow.py:1203` (outbox delivery), `flow_tasks.py:1173-1177` (`_paused_now` for starts), `flow_terminal.py:938-942` (terminal tool), watchdog in `flow_recovery.py`, `AutomationController.tick` (`automation.py:477-`). A separate admission hold (not the pause flag — reasons must read `boot_confirmation_required`, not `paused`) must be threaded into the same points.
- **Missing**: `confirm-boot` CLI showing environment/execution conditions (C-D58 says CLI is enough; UI only shows "확인 대기").
- **Risk (important)**: `ProcessRef` has no boot id (`runtime/process_evidence.py`, `panes.py:45-50`). After a reboot pids and start_ticks restart from small numbers, so probing an old-boot ref can falsely report `alive` (pid reuse with colliding start ticks is plausible right after boot). Reconcile must not probe any ref recorded under another boot id; they are "ended by reboot" by definition. `LifecycleCoordinator.reconcile` (`lifecycle.py:440-449`) probes regardless → must be gated by the boot check (or the startup reconciler must not call it for an old-boot record).
- `read_boot_id()` None → must be treated as `boot_marker_unknown` = confirmation required (fail closed), not "same boot".

### 2.2 Restart reconcile with /proc identity (C-AC-16)
- **Missing**: a startup step. `_open` (`service.py:218-312`) prepares the OMP home, opens stores, constructs `TaskFlow` (its `_load` already mutates: closes unstarted Tasks, holds Tasks with runs), creates `UiServer`, **overwrites backend.json**, spawns three new panes, starts flow/automation/terminal/watchdog. No comparison of the previous incarnation's process refs with `/proc` happens anywhere.
- UI requests are effectively not served until `_open` returns (the loop polls the socket only in `_tick`), so placing reconcile at the top of `run()` (after `InstanceLock.acquire`, `service.py:182-187`) and before `_open` satisfies "UI·자동 동작 전" with no UI change.
- **What a restarted backend sees** (same boot, previous backend SIGKILLed):
  - Previous PTY masters were held only by the backend (CLOEXEC/`closerange`), so the kernel hangs up each pane tty: the session leader of each pane (each OMP, the host shell) gets SIGHUP+SIGCONT; bash then HUPs its jobs. Experiments/children that ignore SIGHUP, `nohup`, or `setsid` daemons survive and are reparented (supervisor subreaper `terminal/shell_g2/lifecycle.py:594` dies on default SIGHUP, so its orphans go to the next subreaper/init). OMP's own SIGHUP handling (bun) is **unknown** — must be observed, not assumed (C-AC-16 says survival is not guaranteed either way).
  - A surviving old OMP's bridge extension retries `bridge.sock` (`bridge.ts:1073-1085`) with its old token; the new backend's new tokens should reject it. Unverified at runtime → include in the restart test.
  - The new backend cannot reattach to surviving processes (the old PTY master is gone): no output capture, no input. Their run can only be `unknown`. Raw log of the old run stops at the kill.
  - Nothing currently kills or reports survivors; they are invisible orphans. (Decision D1.)
- **Journals after restart** (all no-replay, which is correct, but not reconciled with /proc or surfaced):
  - `workflow/tasks-flow.jsonl` → `flow_tasks.py:424-445` holds the Task (`backend_restarted`); the run row in `tasks.sqlite3` stays non-terminal; repository is not told that the run's execution is unknown/interrupted.
  - `lifecycle.json` keeps the last bound run's record (old pids/session ids); the next bind CASes generation+1 (`automation.py:440-443`) — fine, but nobody reads it at start.
  - Handoff outbox (`flow.py:768-776`) loses queued, never-submitted messages silently; terminal journal marks in-flight commands `unknown` (`flow_terminal.py:1117`).
  - Per-run pause journal is not rebound; the global paused flag resets to False (`automation.py:270`) → **pause is lifted by a crash** (gap; SPEC L170).
  - `backend.json` restarts/kills history is lost (overwritten).
- **Model error / metadata failure during the old incarnation** are not durable (only `LifecycleRecord.model_hold`, never set).

### 2.3 RecoveryPort SQLite production implementation
- **Missing entirely** (`policy/recovery_manager/port_sqlite.py` does not exist). Production uses `_NoRecoveryFacts` (`automation.py:233-238`) → `decide` raises/returns blocked; every stop/force is refused (`automation.py:240-241`, doc `automation.py:35-38`).
- `RecoveryFacts` (`policy.py:322-385`) needs: identity/current identity (TaskRepository run row + current run), approval hash (computed exactly as `automation.py:96-102 approval_hash`), `CompletionCriteria` (TaskSpec `execution.criteria`), approved paths (scope decision), `automation_state` (the `_base_state()` dict `automation.py:281-285`), `revoked` (`repository.revoke_authority` `tasks/repository.py:574`), `metadata_healthy` (gate), `terminal_owner` (host shell `input_owner`), `settings_revision`/`authority_version` (repository), `RunObservation` (see 2.4), worker judgment (`WorkerJudgment.from_cw11_report` `policy.py:159`) from the persisted report, raw log/result `Artifact`s (digest + collected sha from `WorkflowRun._record`, `run.py:219-240`), retry `attempts`.
- `reserve_recovery` needs an atomic per-Task CAS (BEGIN IMMEDIATE) — no table exists. Proposal: a port-owned SQLite file `workflow/recovery.sqlite3` (0600) so `TaskRepository`'s schema/migrations (`repository.py:135-180`) are untouched; read TaskRepository through its public getters on a separate connection.
- Consistency risk: TaskFlow counts *all* experiment re-runs against `RETRY_LIMIT=3` (`flow_tasks.py:110,296,678`), CW-13 counts only `recovery` attempts. The port must map TaskFlow runs to `initial`/`normal_improvement` and only reservations to `recovery`; it must not change TaskFlow's limit (CW-13/CW-18 territory). Production only *needs* the stop/force path now (TaskFlow decides re-runs itself); `evaluate/recover` facts should still be correct but are not newly wired into TaskFlow.

### 2.4 Termination callbacks normal_stop / drain / force + termination observation; full shutdown (C-AC-22)
- `termination=lambda: None` (`automation.py:453`) → `reconcile` can never conclude `ended`; `shutdown()` always reports `full_termination_unconfirmed`. Needs a real `RunObservation` from the bound `WorkflowRun`/`ShellPane` lifecycle (`shell.poll` lifecycle: `experiment_started`, `main_exit`, `lifetime`, `input_returned`, `control_returned`, descendants), with a monotonic sequence per run; free-work runs (`FreeWorkProcess`, `automation.py:205-216`) report the worker OMP.
- `normal_stop`: real actuator on the exact ref (pidfd + start-ticks recheck): host shell/run target → the same SIGHUP/SIGTERM-of-owned-session path as C-D63 (`panes.py:212-238`, `SHELL_KILL_GRACE`), OMP → `OmpPane.terminate` (`panes.py:414-423`). `drain` → bounded pane pump. `force` → pidfd SIGKILL of the exact `ForceTarget` only after `decide(kind="force")` authorizes it.
- Authorization path for a user-confirmed full shutdown: `RecoveryCoordinator.decide(kind="stop")` returns `request_stop` only if `facts.revoked` (checked first, `policy.py:500-505`) or automation is allowed & terminal owner is workbench. Proposal: on `shutdown_confirm`, durably revoke the current run's authority (`repository.revoke_authority(..., "user_full_shutdown")`) and commit `admission_closed/shutdown_confirmed` via `LifecycleCoordinator.shutdown` (the at-most-once stop fence, `lifecycle.py:663-676`), then run the existing pane close, and report `verified` only when coordinator result (`ShutdownResult.verified`) **and** exact process evidence are both clean.
- Current gaps in shutdown: `_active_work` (`service.py:642-664`) does not list previous-incarnation survivors or setsid'd descendants (`panes.py:833` `_left_session` exists for display); `_close` evidence covers only pane leaders + supervisor (`service.py:511-520,496-499`); a failed record write in `_close` is swallowed (good) but a later start does not show "previous shutdown unverified". CLI already refuses without tty/`--yes` and exits≠0 when not verified (`cli.py:268-288`) — keep.
- Never auto re-run after a user shutdown (C-AC-22): TaskFlow `_load` already holds; add the `shutdown_confirmed` classification so the next start says "사용자 전체 종료 뒤" rather than "crash".

### 2.5 Fault display (C-AC-17/24/28)
- **Model error**: no event. Needs `bridge.ts` to emit e.g. `model_error {stopReason, errorMessagePresent, sessionId, generation}` (no message text) on any assistant `message_end` with `stopReason error/aborted` or `errorMessage` (next to `bridge.ts:1304`). Backend: set a backend-level `model_hold:<role>` + `LifecycleCoordinator.model_failed` (durable, `lifecycle.py:557-561`) for the bound run; automatic review/notices held (`_automatic_admission` already checks `model_hold`, `lifecycle.py:493-494`); experiment and raw-log collection continue (TaskFlow keeps collecting). `model=SimpleNamespace(check=lambda: False)` means `recheck_model` can never succeed → replace with a passive check (Decision D4).
- **Metadata failure**: `MetadataAdmissionGate` never fed. Sources: TaskRepository write errors (sqlite3.OperationalError), flow ledger append `OSError` (`flow_tasks.py:468-473` re-raises), handoff journal, lifecycle journal, `backend.json` writes. **Robustness gap**: `_write_record` (`service.py:534-535`) is called from the loop (`_check_ready` etc.) without try → an unwritable data dir raises out of `_loop` → backend failure → `_close` kills all panes. That turns a metadata fault into a full stop, violating C-AC-28 "실행·관측 유지". Must become fail-soft + latch the gate.
- **Raw log cap/failure**: experiment raw logs must go through `RawLogStore` (64 MiB run / 512 MiB project, `cap_source`, missing bytes) instead of the unbounded append at `run.py:179-185`; a store failure must mark missing bytes and keep collecting (today an OSError in `_drain` escapes `collect`). Status needs `raw_log: {stored, cap_source, missing, error}` in the task/run view and UI text.
- UI: product status line has no slot for these (`ui/product/model.py:1962,2012-2020`).

## 3. Proposed implementation plan (4 sequential units)

Write scope beyond the PLAN hint (`app/recovery*.py`, `backend/boot*.py`, `policy/recovery_manager/port_sqlite.py`, `tests/recovery_boot/**`, `tests/vm/**`) is required; Root must widen the lease. Files shared with the concurrent polish writer (flow*.py, bridge.ts) must be taken **after** that polish is integrated (rebase on its commit).

### U1 — Boot marker, startup reconcile, admission hold, durable pause (worker_senior, Opus)
Behaviour:
1. `backend/boot.py` (new): `BootStore` at `<data>/boot.json` (0600, atomic+fsync like `LifecycleJournal._write`): `{version, recorded_boot_id, confirmed_boot_id, pending: bool, history[≤20]}`. `classify(previous_record, boot_state, current_boot_id)` → `fresh | same_boot_clean_stop | same_boot_crash | same_boot_unverified_stop | reboot | boot_unknown`.
2. `app/recovery.py` (new): `StartupReconciler.run()` — called in `Backend.run()` right after the instance lock and **before** `_open` (so before any pane spawn, any record overwrite, TaskFlow `_load`, UI serving). It:
   - reads the previous `backend.json` and keeps it as `backend.prev.json` (+ bounded history in `workflow/recovery/`);
   - same boot only: probes every previous exact ref (backend, manager/worker OMP, host shell, supervisor, LifecycleRecord run targets) with `LinuxProcessProbe` → `alive/dead/unknown`; different/unknown boot: marks all as `ended_by_reboot` **without probing** (pid-reuse guard);
   - reads `lifecycle.json`, the current run in `tasks.sqlite3`, `tasks-flow.jsonl` open Tasks, terminal journal in-flight commands; produces a `ReconcileReport` (persisted 0600, shown in snapshot `recovery.startup`): per item `recovered | held_unknown | ended_by_reboot | survivor_not_owned_now`, never replays;
   - reboot/boot_unknown: sets `pending=True` durably **before** the backend serves anything; a run that was running is recorded as `interrupted_by_reboot` (outcome unknown, never success) and its Task stays held (TaskFlow's `backend_restarted` hold already prevents re-run).
3. Admission hold (`app/recovery.py` `AdmissionHold`): reasons `boot_confirmation_required | boot_marker_unknown | metadata_unavailable | model_hold:<role> | shutdown_closing`. Threaded as an extra callable into `HandoffService` (to_worker → `held("boot_confirmation_required")`), TaskFlow start/runner, TerminalService (terminal tool), Watchdog notices, AutomationController tick (problems list). User direct pane input, pane restart (C-D62/63), takeover, pause/resume, cancel, status stay allowed (Decision D3).
4. `confirm_boot` (`service.py:683`): require pending + exact current boot id, persist `confirmed_boot_id` + `pending=False` first, then lift; also `LifecycleCoordinator.confirm_boot` for a bound record if any. CLI `python -m workbench confirm-boot [--yes] [--json]`: prints boot ids (recorded/current), data/project dir, shell, OMP version + isolation result, held Tasks/interrupted runs, worktrees, pause state; asks y/N (tty) or `--yes`; sends `CONFIRM_BOOT` with the boot id it read from the snapshot; exit≠0 on mismatch/no pending. `status` prints pending + startup reconcile summary.
5. Durable global pause: persist the AutomationController paused flag (backend-level file, e.g. `<data>/automation.json`) on every transition; restore `paused=True` at start (resume still requires `reconciled: true`).
6. `_write_record` fail-soft (catch OSError, latch metadata failure via U3 hook; in U1 just log + keep running).
7. UI: status-line text for boot pending ("재부팅 확인 대기: `python -m workbench confirm-boot`"), startup recovery summary (held/unknown/survivors), and the hold reason on held actions.

Write scope: `src/workbench/backend/boot.py`, `src/workbench/app/recovery.py`, `src/workbench/backend/service.py`, `src/workbench/backend/cli.py`, `src/workbench/backend/paths.py` (new paths), `src/workbench/backend/automation.py` (paused persistence, hold in tick), `src/workbench/backend/flow.py`, `flow_tasks.py`, `flow_terminal.py`, `flow_recovery.py` (hold hook only — after polish integration), `src/workbench/ui/product/model.py`, `tests/recovery_boot/**`.
Unit tests (`tests/recovery_boot/`): classify matrix (fresh, clean stop, crash, reboot, boot id None, corrupt boot.json → fail closed); old-boot refs never probed (fake probe asserts zero calls) while same-boot refs are probed with pid+start_ticks; survivors listed, never signalled; reconcile runs before TaskFlow construction and before `UiServer` accept (ordering test with a spy); confirm-boot persistence across a simulated crash (pending survives restart; confirmed survives restart); holds return `held:boot_confirmation_required` for to_worker/terminal and no Task/outbox entry is created; paused restored after restart; `_write_record` OSError does not stop the loop; CLI `confirm-boot` refuses without tty/`--yes`, refuses mismatched id.

### U2 — SQLite RecoveryPort + real termination/stop callbacks + full shutdown (worker_senior, Opus)
Behaviour:
1. `policy/recovery_manager/port_sqlite.py`: `SqliteRecoveryPort(tasks_db, recovery_db, run_facts)` — `read(identity)` builds `RecoveryFacts` from TaskRepository (read connection), the run's `result.json` record, the persisted worker report, scope approval, settings; `reserve_recovery` = `BEGIN IMMEDIATE` CAS on `recovery_attempts(task_id, decision_id UNIQUE, ordinal)` checking expected_used/authority/settings/maximum; fail → False. Any read gap raises (coordinator fails closed).
2. `automation.py` `_bind_lifecycle`: pass `RecoveryCoordinator(SqliteRecoveryPort(...))`; `termination` = `RunObservation` from the bound run (sequence counter, shell lifecycle facts; free work → worker OMP liveness); `normal_stop` = exact-ref actuator (pidfd + start-tick recheck; shell session HUP/TERM per C-D63 path; OMP SIGTERM to its pgid); `drain` = bounded wait/pump; `force` = pidfd SIGKILL of the exact authorized target. Remove `_NoRecoveryFacts`, `_refuse_stop`.
3. Full shutdown (`service.py` `shutdown_request/confirm`, `_close`): request lists active work incl. previous-incarnation survivors (from U1 report, re-probed) and setsid'd descendants (display only); confirm → durable `shutdown_confirmed` marker in boot/record, revoke the current run's authority (`user_full_shutdown`), `LifecycleCoordinator.shutdown(user_confirmed=True)` when a run is bound, then existing flow/pane close; `verified = coordinator.verified and all exact refs dead`; result (survivors, problems) persisted to `backend.json` and shown by CLI; next start classifies `same_boot_unverified_stop` and shows the leftovers.
Write scope: `src/workbench/policy/recovery_manager/port_sqlite.py`, `src/workbench/app/recovery.py`, `src/workbench/backend/automation.py`, `src/workbench/backend/service.py`, `src/workbench/backend/cli.py` (output only), `tests/recovery_boot/**`. (No TaskRepository schema change.)
Unit tests: port facts mapping vs `policy.py` validators (identity mismatch, approval changed, revoked, metadata unhealthy); reserve CAS (duplicate decision id, stale expected_used, limit, concurrent reservations from two threads/processes → exactly one wins); `decide(stop)` after revoke authorizes `request_stop` and the actuator signals only the exact ref (pid reuse with different start ticks → no signal); termination observation sequence monotonic and `fully_terminated` only with descendants clear; shutdown not verified when a survivor remains, CLI exit≠0, survivor listed; no stop is repeated after a crash between the durable fence and the stop (fence test).

### U3 — Fault signals and display: model error, metadata failure, raw log cap (worker_senior)
Behaviour:
1. `omp_bridge/g3/bridge.ts`: `model_error` event (role, stopReason ∈ {error, aborted}, errorMessagePresent, sessionId, generation; never message text) on assistant `message_end` with error, independent of deliveries.
2. Backend: `model_error` → backend `model_hold:<role>` (+ `LifecycleCoordinator.model_failed` for a bound run) → admission hold for automatic model work of that role (review, notices, TASK/follow-up delivery); experiment collection, raw log, terminal observation continue; hold lifts per Decision D4 (default passive: next assistant turn of that role ends without error) → `recheck_model` records success. UI: "모델 오류(worker): 자동 작업 보류, 실험·관측 계속".
3. Metadata: wrap TaskRepository writes / flow ledger / handoff journal / lifecycle journal / record writes failures → `MetadataAdmissionGate.record_metadata_failure`; successful durable write → `record_durable_metadata_success`. Hold = `metadata_unavailable` for new Tasks/runs/notices; running experiment and raw logs continue. UI text.
4. - R3 `_write_record` exceptions currently crash the backend on an unwritable data dir (metadata fault → full stop). Fix in U1/U3.

## 5. Decisions needing the user (defaults proposed, not decided)
- **D1 Previous-incarnation survivors after a backend crash** (old OMP, host-shell children, experiment): default **display only, never signalled** (SPEC: force only on confirmed, authorized targets; C-AC-16 no survival assumption); they appear in `status`, the UI recovery line and the `shutdown` active list. Alternative: include them (exact pid+start_ticks+same boot) in the confirmed full shutdown cleanup.
- **D2 Manager notice after a same-boot backend restart with an open Task**: default **inject one "backend 재시작" recovery notice into the new manager session after reconcile** (same as C-D70 (4) for a new manager session; never while paused, never before confirm_boot, never with metadata/model hold). Alternative: display only; the manager learns on its next tool call.
- **D3 What "새 실험과 자동 모델 작업" holds before confirm_boot**: default hold **all Workbench-originated automatic actions** (to_worker dispatch of both experiment and free-work Tasks, worker `terminal` tool, watchdog/recovery notices, 60 s review); allow user direct pane input, pane restart (C-D62/63), takeover, pause/resume, cancel, status.
- **D4 Model-error re-check**: default **passive** — the hold lifts when the same role's next assistant turn ends without error (e.g. the user's own prompt); Workbench sends no probe request (no model cost). Alternative: an explicit user "recheck" CLI/UI action.
- **D5 Project 512 MiB cap scope**: default experiment run raw logs through `RawLogStore`; worker terminal command logs keep their 64 MiB/command cap and are **not** counted in the project cap (documented difference). Alternative: count terminal logs in the project cap.
Out of scope (ticket): backend auto start after reboot; automatic re-run of a pre-reboot experiment; host reboot.
