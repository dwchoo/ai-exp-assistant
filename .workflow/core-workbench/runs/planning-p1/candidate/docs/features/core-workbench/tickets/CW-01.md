# CW-01: M0 harness와 임시 공통 계약

명세: [SPEC.md](../SPEC.md) s1. Scheduling·resource·scope의 원본: [PLAN.json](../PLAN.json) CW-01 항목. Live 상태와 작업 배정은 Root의 별도 workflow state에서 관리한다.

## 제공할 동작

최소 Python package·TS contract test harness를 만들고, 세 PTY/두 OMP/host shell이 공유할 versioned control envelope와 Task·revision·run·command·message·session 식별 규칙을 정의한다. 이 ticket은 제품 기능이나 외부 라이브러리의 호환 통과를 선언하지 않는다.

## 수락 기준

- M0: 위 제공 동작을 실제 조건에서 검증하고 재현 가능한 통과·실패·미확인 근거를 남긴다. 수락 ID는 직접 소유하지 않으며 후속 C-AC 검증의 선행 증거다.

## 계약과 선행 산출물

- 승인된 BRIEF r1.7과 현재 repository baseline을 시작점으로 삼는다.

승인된 BRIEF r1.7 byte snapshot과 현재 untracked 입력을 보존한다. PTY display byte와 control event를 분리하고 접수·실제 시작·실제 완료·불명을 다른 상태로 표현한다. Gate 산출물의 OMP/shell/terminal 버전, 명령, 조건, 결과를 남길 형식을 정한다.

계획 write scope: `pyproject.toml`, `src/workbench/contracts/**`, `tests/contracts/**`, `omp_bridge/contract/**`, `tests/gates/harness/**`. 실제 dispatch 전에 Root가 current base·소유권·resource claim을 다시 확인한다.

## 검증

계약 직렬화·역직렬화와 잘못된 version/role/session/중복 ID 거절, harness의 실제 실행을 확인한다. 이후 ticket의 명령을 문서화한다. 독립 test_designer가 contract test 누락을 평가하고 reviewer가 과도한 lock/추상화를 점검한다.

공통 검증: worker quick check → 독립 test_designer 평가/필요 테스트 → 동결 후보 fresh reviewer → 필요한 수정·delta review → Root 통합 및 SPEC의 최종 check. 명령·cwd·candidate·환경·결과를 기록한다.

## 범위 밖과 중단 조건

제품 API가 아직 없는 상태에서 특정 library/OMP 동작을 성공으로 고정하거나 BRIEF 동작을 좁혀야 하면 중단하고 CW-02~05의 실증 대상으로 남긴다.

Phase 2·내부 외부 multiplexer·무단 commit/push/merge·미승인 제품 동작 확대는 이 ticket의 범위가 아니다.

## 산출물 인계

변경 경로와 근거를 특정한 candidate/output bundle, 실제 수행한 check와 미실행 사유, 실패·미확인 gate/acceptance, 다음 ticket이 소비할 계약 변경점을 Root에게 전달한다. Ticket 작성자가 PLAN/state/approval을 직접 바꾸지 않는다.
